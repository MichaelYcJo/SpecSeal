# smith 를 스폰하면 자국이 남고, smith 로 선언하고 아무도 스폰하지 않으면 한 번 알립니다

<!-- PR #<번호> 본문의 한국어판. 영어 본문이 정본이고 이 파일이 번역입니다. -->

라우팅 선언의 셋째 축 `Implementation` 은 0.2.0 부터 있었지만, 그 답을 읽는
것이 아무것도 없었습니다. `smith` 라고 적어 두고 세션이 직접 구현해도 아무도
모릅니다. 이 변경은 그 축을 확인 가능한 것으로 만듭니다. 원래 작업 항목은
히스토리 재작성 전 브랜치에 미완성으로 남아 있었고, 열어 보니 코드는 완성돼
있었고 없던 것은 기록이었습니다.

## 무엇이 달라지나

| | 이전 | 이후 |
|---|---|---|
| `smith` 를 스폰할 때 | 아무 흔적 없음 | `.git/specseal-implementer` 에 브랜치 이름이 적힙니다. 출력도, 질문도 없습니다 |
| `routing.md` 가 `smith` 인 브랜치에서 커밋했는데 자국이 없을 때 | 아무 일 없음 | 커밋 뒤 한 줄 알림이 저장소당 세션당 한 번 나옵니다. 막지 않습니다 |
| `.specseal/` 이 없는 저장소 | 아무 일 없음 | 그대로 아무 일 없음. 파일도 만들지 않습니다 |
| worktree 가드의 판정 | — | 그대로입니다. 새 게이트가 같은 그룹에 들어가도 판정은 바뀌지 않음을 실행으로 확인했습니다 |

**질문을 하나도 늘리지 않습니다.** 자국은 게이트 판정 전에 조용히 쓰이고, 알림은
PostToolUse 라 결정을 낼 수 없는 자리에서 출력만 합니다. 알림이 보지 못하는
커밋 형태(`eval`, `bash -c`, heredoc 본문 안, 루프 첫 문장)는 의도된 사각이고,
놓치면 알림 한 번을 잃을 뿐 결정에는 닿지 않습니다.

## 이슈 #26 에 대하여

이 저장소의 #26 은 바로 이 설계를 만들지 않기로 한 기록입니다. 반대 근거
둘 중 측정 가능한 것(새 게이트가 worktree 가드를 함께 죽인다)은 측정해서
성립하지 않음을 확인했고, 다른 하나(질문이 늘어난다)는 설계상 0 입니다.
소유자가 라우팅으로 이 작업을 지시했으므로 만들었고, #26 을 닫을지 고칠지는
`questions.md` Q1 로 소유자에게 남겼습니다.

## 리뷰 체인

한 라운드로 끝났습니다. 리뷰어가 두 훅을 직접 여러 페이로드로 돌려 결정을
내지 않음과 가드 판정 불변을 확인했고, 코드 결함은 없었습니다. 🟡 둘은 기록의
문장이었고(모든 파일 열기가 utf-8 을 명시한다는 문장에 예외 하나, 알림의 사각을
대조표가 말하지 않던 것) 같은 커밋에서 고쳤습니다.

## 검증

수치는 영어 본문의 표에 있습니다.

| 검사 | 결과 |
|---|---|
| 전체 테스트 스위트 (3.12) | 통과 |
| 새 테스트 17개 + 라우팅·리뷰 축·dispatch 테스트 | 통과, skip 없음 |
| 변이 검사 11건 (바이트코드 캐시 끄고) | 각각 자기 테스트만 실패 |
| dispatch 프로브 — smith / 비smith / 옵트인 안 한 저장소 × worktree 격리 유무 | 가드 판정 동일, 자국은 옵트인 저장소의 smith 에만 |
| ruff check · ruff format | 통과 |
| 근거 대조표 (`evidence-check --strict`) | 새 행 6개 포함 전부 해석 |
| 체인 · 미검증 항목 검사기 | CI 와 같은 호출로 exit 0 |

실제 하네스에서 smith 를 스폰해 자국이 생기는지, 그리고 PostToolUse 의 출력이
사람에게 보이는지는 머지 뒤 첫 세션에서 소유자가 확인할 항목으로 overview 에
남겼습니다.
