# 플러그인이 관리하는 루트 하나, 수명 순으로 배치한다

*[English](./one-root-by-lifetime.md) · 한국어*

0.4.0 이 출발점으로 삼는 설계입니다. 이슈 #74 본문과 그 아래 코멘트 열 개를
한 문서로 모았습니다(2026-09-02, 0.3.0 출시 뒤). 여기 적힌 것 중 0.3.x 에
들어가는 것은 없습니다. 아래 이름은 모두 소유자가 정하기 전까지 임시
이름입니다. 스레드에서 한쪽으로 기운 자리는 *권장* 이라고 적고 이유를
붙였습니다. 결정할 것은 맨 끝 「결정을 남겨 둔 것」에 모아 두었습니다.

이 문서의 숫자는 2026-09-02 에 `origin/main` 의 `5685029`(0.3.0 병합 커밋)
기준으로 다시 잰 것입니다. 이슈에 적힌 숫자와 다른 자리는 둘 다 적었습니다.

## 무엇이 바뀌는가, 네 줄로

지금은 커밋되는 루트 둘에 사는 기간이 세 가지로 다른 파일이 섞여 있고, 어느
루트도 그 기간으로 자리를 나누지 않습니다. `specs/<id>/` 에는 작업 항목의
문서와 리뷰 기록이 함께 있는데 둘은 없어지는 시점이 다릅니다.
`.specseal/` 에는 근거 대조표(스펙 조항과 코드 좌표를 짝지어 둔 표)가 있는데,
그 행은 자기를 쓴 작업 항목보다 오래 삽니다. 바뀐 뒤에는 플러그인이 관리하는
루트 하나가 전부를 담고, 얼마나 오래 사는지에 따라 자리를 나눕니다. 옵트인
신호는 트리 밖 로컬 git 상태로 옮겨 가고, `specs/` 는 SpecSeal 이 읽기만
하고 쓰지 않는 디렉터리가 됩니다.

```
지금                                        바뀐 뒤
────                                        ──────
specs/<id>/   spec plan questions overview   seal/specs/<id>/     작업 항목 전체
              routing rounds/ todos pr.ko   seal/ledger/<id>.md  그 항목의 행, 릴리스까지
.specseal/    map.md map/<id>.md             seal/ledger.md       합쳐진 근거 대조표
              follow-up.md parity.md         seal/follow-up.md seal/parity.md
(.specseal/ 가 있다)  = 옵트인               git config specseal.*  = 옵트인
```

## 문제를 숫자로 보면

| 관찰 | `5685029` 에서 잰 값 | 이슈의 값 | 무엇을 말하는가 |
|---|---|---|---|
| 일주일 뒤의 `specs/` | 작업 항목 13 · 파일 101 · 6,937 줄 | 13 · 96 · 6,655 | 병합 뒤에는 라운드 기록을 기계가 읽지 않고, 사람도 거의 읽지 않습니다 |
| `.specseal/map/` | 조각 파일 6 개, `map.md` 와 `map/` 을 합쳐 앵커 행 79 개 | 살아 있는 행 83 개 | 행 수는 살아 있는 주장의 수에 묶여 있어 괜찮습니다. 파일은 작업 항목마다 하나씩 영원히 남고, PR 을 올릴 때마다 거의 매번 이 디렉터리에 손이 갑니다 |
| `specs/` 는 spec-kit(GitHub 의 스펙 주도 개발 도구. `specs/NNN-feature/` 에 씁니다)의 디렉터리이기도 합니다 | — | — | 도구 둘이 한 폴더에 씁니다 |

이슈의 숫자는 이 문서보다 먼저 센 것입니다. 무엇을 다르게 셌는지는 추적하지
않았습니다.

`specs/` 줄 수의 절반은 `rounds/` 와 `overview.md` 입니다. 각각 2,147 줄과
1,279 줄입니다.

이 셋은 결함 하나입니다. **수명이 다른 것이 한 폴더를 쓰고, 수명이 같은 것이
두 폴더로 갈라져 있습니다.**

| 무엇 | 실제 수명 | 지금 있는 자리 |
|---|---|---|
| spec · plan · questions · overview | 그것을 싣는 릴리스까지. 그 뒤로는 git 이력과 CHANGELOG 의 작업 항목 주석이 보존합니다 | `specs/<id>/` |
| routing · rounds · todos | PR 이 열려 있는 동안. 커밋 게이트와 `chain_check.py` 가 읽습니다 | `specs/<id>/` |
| 근거 대조표의 행 | 그 행이 가리키는 코드가 살아 있는 동안. 작업 항목보다 깁니다 | `.specseal/map/<id>.md` |
| follow-up · parity | 저장소가 살아 있는 동안 | `.specseal/` |

### 사람의 파일과 도구의 파일, 경계는 어디에 있는가

"`specs/` 는 보이게, `.specseal/` 은 숨기게" 라는 기준은 이 도구가 없었어도
사람이 그 파일을 쓰고 읽었을까 하는 물음이었습니다. 그 기준은 `specs/` 폴더의
경계와 일치하지 않습니다.

| 사람의 것, 스펙 주도 개발(SDD)이 정한 표준 형태 | 도구의 것, SpecSeal 의 어휘 |
|---|---|
| `spec.md` · `plan.md` · `questions.md` · `overview.md` · `changelog.md` | `routing.md`(경로를 정하지 않은 커밋을 멈추는 훅인 커밋 게이트가 읽음) · `rounds/round-N.md`(선언한 리뷰 체인에 기록이 있는지 PR 에서 확인하는 `chain_check.py` 가 읽음) · `tests-todo.md` · `evidence-todo.md` |

작업 항목 안에서 두 종류를 갈라 놓는 일은 소유자의 결정으로 범위 밖입니다.
라운드 기록은 PR 이 열려 있는 동안 트리 안에 있어야 하고, 그것을 스펙과 떼어
놓는 일은 이 변경보다 큽니다. 그래서 아래 설계는 `specs/` 에 도구의 파일이
없다고 가정하지 않습니다. 이 경계는 릴리스 뒤에 무엇을 남길 가치가 있는지
정할 때만 씁니다.

## 제안하는 트리

플러그인이 관리하는 루트 하나입니다. "플러그인이 관리한다" 는 것은 플러그인이
만들고 옮기고 비우며, 그 검사기가 형식을 정한다는 뜻입니다. `.github/` 가
GitHub 의 것인 것과 같습니다. 기본 모드에서는 커밋합니다. 근거 대조표와
라운드 기록이 CI 와 다른 클론에 닿아야 하기 때문입니다.

```
<repo>/
├── seal/                          플러그인이 만들고 옮기고 비운다. shared 모드에서는 커밋한다
│   ├── README.md                  이 폴더의 규칙: 옮기기 규칙, 무엇이 언제 사라지는지
│   ├── ledger.md                  합쳐진 근거 대조표 — 영구
│   ├── ledger/<id>.md             진행 중인 작업 항목의 행 — 릴리스 때 ledger.md 로 합치고 지운다
│   ├── follow-up.md               영구
│   ├── parity.md                  이관 프로젝트에만 — 영구
│   └── specs/<epoch>-<slug>/      작업 항목 전체 — 릴리스 뒤에 무엇이 남는지는 「보존」 절
│       ├── spec.md plan.md questions.md overview.md      사람이 읽는 것
│       ├── changelog.md                                  릴리스 때 CHANGELOG.md 로 모은다
│       ├── routing.md rounds/round-N.md                  커밋 게이트와 CI 가 읽는 것
│       ├── tests-todo.md evidence-todo.md                릴리스가 무엇이든 지우기 전에 evidence-todo 는 비어 있어야 한다
│       └── pr.ko.md
├── docs/                          정책서. 릴리스보다 오래 살아야 할 의도가 사는 자리. 그대로
├── specs/                         SpecSeal 이 쓰지 않는다. 있으면(spec-kit, 사람) 정책 입력으로 읽는다
├── CHANGELOG.md                   그대로
└── .git/                          세션 상태. 커밋하지 않는다. 그대로
    ├── specseal-implementer       smith 표시(mark. smith 에이전트를 띄우면 남는 파일)
    ├── specseal-worktree-choice/  워크트리 질문의 답
    └── config                     specseal.mode / specseal.optin — 옵트인 신호. 클론마다, 또는 --global
```

수명은 셋이고, 각각 집이 하나입니다.

| 수명 | 사는 자리 | 끝나는 때 |
|---|---|---|
| 세션 | `.git/` | 세션이 끝날 때 |
| 릴리스와 릴리스 사이 | `seal/specs/<id>/` 의 도구 파일 · `seal/ledger/<id>.md` | 릴리스 준비 단계가 돌 때 |
| 영구 | `seal/ledger.md` · `follow-up.md` · `parity.md` · `docs/` · `CHANGELOG.md` · 제안한 보존 기본값에서는 `seal/specs/<id>/` 의 사람 파일도 | 없음 |

`retain = none` 이면 사람의 파일이 가운데 줄로 가고, `all` 이면 도구의
파일이 마지막 줄로 갑니다.

지금과 견주면 루트 자체는 세 가지가 바뀝니다. 루트 둘이 하나가 되고, 옵트인이
디렉터리의 존재에서 로컬 설정 키로 옮겨 가고, 작업 항목 디렉터리와 대조표
조각에 수명이 생깁니다. 그 위에 뒤의 코멘트들이 더한 것이 있고, 아래 절들이
그것을 담습니다. 처음 설정할 때 묻는 두 가지, 보존 규칙, export/import 한
쌍입니다.

**이름이 드러내는 관계.** 최상위 `specs/`(spec-kit 의 것, 사람의 것)는 seal
이 봉인하는 대상입니다. `seal/specs/<id>/` 는 봉인된 사본에 과정 기록을 붙인
것입니다. `seal/ledger*` 가 seal 그 자체입니다. 스펙과 코드를 묶어 두고,
코드가 움직이면 깨지는 그 묶음입니다.

## 릴리스 때 일어나는 일

누적 문제 둘은 릴리스 준비 단계의 규칙 하나로 끝납니다. 스레드는 "릴리스
준비 스크립트" 라고만 했습니다. 이 문서는 그것을 지금 손으로 `changelog.md`
조각을 모으는 단계(`.github/scripts/gather_changelog.py --version`,
`docs/branch-and-release.md` 참조)로 읽었습니다.

1. 릴리스된 작업 항목의 `seal/ledger/<id>.md` 를 `seal/ledger.md` 로 합치고
   조각을 지웁니다. 아직 병합되지 않은 작업 항목의 조각은 그대로 둡니다.
2. 릴리스된 작업 항목의 `seal/specs/<id>/` 를 아래 보존 설정에 따라
   비웁니다.
3. **비우기 전의 가드.** 릴리스보다 오래 살아야 하는 `spec.md` 의 문장은
   병합 전에 `docs/` 정책서나 대조표의 행으로 옮겨져 있어야 합니다. 지금은
   `evidence-todo.md` 가 그것을 반쯤 강제합니다. 이 단계가 파일을 지우게
   되면, 작업 항목 어디든 `evidence-todo.md` 에 열린 행이 하나라도 있으면
   돌기를 거부해야 합니다. 이슈는 "어느 작업 항목이든" 이라고 했습니다.
   병합되지 않은 항목은 비우지 않으므로, 이 문서는 그것을 릴리스된 항목
   어느 것이든으로 읽었습니다.

행을 남기지 않고 합치는 이유는 스레드가 아니라 이 문서의 해석입니다. 조각
배치는 애초에 브랜치 둘이 한 파일 앞에 줄 서는 것을 막으려고 생겼고, 병합
뒤에는 줄 설 브랜치가 없습니다.

## 이 뒤로 "spec" 은 무엇을 뜻하는가

그대로입니다. `spec.md` 는 늘 변경 하나의 스펙이었습니다. 변경보다 오래
살아야 하는 것은 이미 집이 둘입니다. `docs/` 정책서(판단 순서는 정책서 >
SDD > 코드)와 대조표의 행입니다. 행은 코드 좌표 옆에 조항 문장을 함께
적습니다. AI 의 작업을 검사하는 사람은 PR 이 열려 있는 동안, `spec.md` 가
있을 때 검사합니다. 릴리스 뒤에 "왜 이렇게 동작하지" 를 묻는 사람은 `docs/`
와 대조표를 읽습니다.

## 옵트인 신호는 트리 밖으로 나간다

커밋해야 하는 것은 검사기가 읽는 것뿐입니다. 근거 대조표(CI 의 `ledger` 잡,
다른 클론)와 `routing.md` / `rounds/`(PR 이 열려 있는 동안 커밋 게이트와
`chain_check.py`)입니다. 신호 자체는 훅이 로컬에서 읽으므로 세 자리 중
어디에든 둘 수 있습니다.

- git 설정 키. `git config specseal.optin true` 로 클론마다, 또는
  `--global` 로 기계마다 켭니다. 연결된 워크트리는 같은 값을 봅니다. 트리에는
  아무것도 남지 않습니다.
- `.git/` 아래의 표시 파일. smith 표시와 워크트리 선택이 이미 거기 있습니다.
  클론마다입니다.
- 가져온 ref 의 존재. 대조표가 언젠가 orphan 브랜치로 옮겨 가면 그 ref
  입니다. 클론을 따라 자동으로 옵니다.

셋 모두 지금의 실패 방향을 지킵니다. 없으면 옵트인하지 않은 것입니다.

**달라지는 것은 뜻입니다.** 지금은 커밋된 루트가 저장소의 선언입니다. 클론하면
모든 협업자의 게이트가 켜집니다. 로컬 신호가 되면 그 클론을 쓰는 개발자의
선택이 됩니다.

그러면 옵트인하지 않은 협업자는 게이트 없이 커밋하고, 저장소 수준의 보장은
CI 의 몫이 됩니다. 대조표 검사와 체인 검사는 옵트인과 무관하게
워크플로에서 돌기 때문입니다. 남에게 배포하는 플러그인에는 이 분리가 맞습니다.
도구를 쓰는 사람이 켜고, 저장소가 강요하지 않습니다. 이쪽을 고르면 루트는
표시 역할을 잃고, 트리에는 검사기가 읽는 것만 남습니다.

| | 지금 | 바뀐 뒤 |
|---|---|---|
| 저장소를 옵트인하는 것 | 루트에 `.specseal/` 이 있다(`hooks/optin.py`) | 로컬 설정 키 또는 `.git/` 표시 파일 |
| 누가 정하는가 | 그 디렉터리를 커밋한 사람이, 모든 클론에 대해 | 개발자 각자, 자기 클론에 대해 |
| 옵트인하지 않은 협업자 | 그래도 게이트에 걸린다 | 게이트 없이 커밋한다. PR 은 CI 가 검사한다 |
| `.specseal/scratch` 옵트아웃 | 버릴 픽스처에서 게이트를 끄는 빈 파일 | 그 용도로는 더 필요 없다. 픽스처는 키를 안 켜면 된다(「결정을 남겨 둔 것」 참조) |

## 처음 설정할 때 묻는 두 가지

이 프로젝트가 질문을 허용하는 유일한 순간이 처음 설정입니다. 그래서 둘 다
그때 묻고 다시는 묻지 않습니다.

### shared 인가 local 인가

"폴더를 커밋할 것인가" 가 아니라 "CI 와 협업자가 이 워크플로를 보는가" 를
묻는 것입니다.

| 모드 | `seal/` 의 자리 | 얻는 것 | 잃는 것 |
|---|---|---|---|
| shared(기본) | `<repo>/seal/`, 커밋 | CI 의 대조표 검사와 체인 검사. 모든 클론과 워크트리에서 같은 상태. 다시 클론해도 기록이 남는다 | 트리의 폴더 하나 |
| local | `.git/seal/`, 커밋하지 않음 | 트리에 아무것도 없다. 이 클론 안에서는 게이트와 리뷰 체인이 그대로 돈다 | 모든 CI 검사. 다른 기계. 다시 클론했을 때의 기록 |

혼자 쓰는 저장소나 남의 트리에 기여할 때는 local 이 맞습니다. 구현은 설정
때 쓰는 키 하나(`specseal.mode = shared | local`)입니다. hygiene
워크플로(`.github/workflows/hygiene.yml` 의 PR 검사)를 설치할지도 같은
플래그를 보고 정합니다. 라운드 기록이 없는 PR 은 그 워크플로에서 거부되기
때문입니다.

**local 모드가 gitignore 가 아니라 `.git/` 아래인 이유.** 연결된 워크트리는
커밋된 파일만 체크아웃합니다. 그래서 메인 트리에서 무시(ignore)한
`<repo>/seal/` 은 모든 워크트리에서 그냥 없습니다. 소유자가 `.specseal/` 을
무시했을 때 병렬 세션이 서로의 기록을 읽지 못한 일이 바로 이것입니다. 설정
실수가 아니라 git 의 동작입니다. 그래서 local 모드는 `seal/` 을 공통 git
디렉터리(`git rev-parse --git-common-dir`, 즉 `.git/seal/`) 안에 둡니다.
smith 표시와 워크트리 선택 기록이 이미 있는 자리입니다. 그 클론의 모든
워크트리가 공유하고, 커밋 후보가 되지 않으며, `.gitignore` 줄도 필요
없습니다.

두 모드에 대한 소유자의 정리를 그에 맞춰 고치면 이렇습니다.

1. 처음 설정할 때 `seal/` 을 커밋 범위에 넣을지 고릅니다. shared 모드는
   `<repo>/seal/` 에 두고 커밋합니다. local 모드는 `.git/seal/` 에 두고
   커밋하지 않습니다.
2. 두 모드 모두 워크트리와 병렬 세션이 서로의 기록을 읽습니다. shared 는
   파일이 커밋되어 있어서, local 은 git 디렉터리가 공통이어서 그렇습니다.
   local 모드에는 커밋 안 된 상태를 브랜치별로 격리하는 장치가 없습니다.
   병렬 항목을 떼어 놓는 것은 작업 항목마다 조각을 두는 배치입니다.
3. local 모드의 기록은 그 기계의 그 클론을 떠나지 않습니다. 새 기계나 새
   클론은 대조표도 작업 항목 기록도 없이 시작하고(좌표는 다시 구합니다), CI
   의 대조표 검사와 체인 검사는 돌 수 없습니다. 이것이 트레이드오프의
   전부입니다.

**두 모드는 서로 바꿀 수 있고, local 의 기록은 손으로 다른 클론에 옮길 수
있습니다.** 대조표의 행은 내용 앵커(`path#unit@hash`, 줄 번호 없음, SHA
없음)라서, 옮긴 대조표는 다른 트리에서 내용이 다른 자리만 DRIFTED(검사기가
"내용이 바뀌었으니 주장을 다시 읽으라" 고 표시하는 상태)로 내려가고 깨지지는
않습니다. 라운드 기록은 푸시된 커밋을 가리킵니다.
`.git/seal/` 은 그것만 복사할 수 있게 자기 폴더여야 합니다. 옆에 있는 smith
표시, 워크트리 선택, 세션 lease(세션이 잡아 두는 임대 표시)는 그 기계의 세션
상태입니다.

복사는 동기화가 아닙니다. 마지막 복사가 이기고, 어느 행이 넘어갔는지는 사람이 기억해야
합니다. 그래서 두 번 필요해지면 shared 로 바꾸라는 신호입니다. 바꾸는 것은
어느 쪽이든 한 번의 이동입니다. `.git/seal/` 을 `<repo>/seal/` 로, 또는
그 반대로 옮기고 커밋하거나 지우면 됩니다. 처음의 선택은 "지금 어디에
두는가" 이지 되돌릴 수 없는 문이 아닙니다.

**local 모드에는 export/import 한 쌍이 붙습니다.** 그러면 트레이드오프가
"잃는다" 에서 "사본을 챙긴다" 로 바뀝니다.

- `seal export` 는 `.git/seal/` 만 `seal-<repo>-<date>.zip` 으로 묶습니다.
  옆의 세션 상태는 넣지 않습니다. 매니페스트에 원격 URL 과 export 시점의
  HEAD SHA 를 적습니다.
- `seal import <zip>` 은 덮어쓰지 않습니다. 파일은 작업 항목 id 로
  구분되므로 없는 것은 추가하고, 이미 있는 id 는 기존 파일 옆에
  `<id>.incoming.md` 로 내려놓고 알립니다. 묻지 않습니다. 그 뒤
  `evidence-check` 가 이 트리 기준으로 어느 행이 어긋났는지 말해 줍니다.
- 같은 쌍이 모드 전환입니다. export 한 뒤 `<repo>/seal/` 에 풀고
  커밋합니다. 반대도 같습니다.
- 알림은 하나뿐입니다. local 모드에서는 릴리스 준비 단계에서 "마지막 export
  이후 작업 항목 N 개가 바뀌었습니다" 한 줄을 보게 됩니다. 어디에도 올리지
  않습니다. 사본을 어디에 둘지는 사용자의 일이고, 플러그인이 묻는 질문이
  아닙니다.

선택지 수보다 기본값이 더 중요합니다.

이 선택과 루트의 이름은 묶여 있습니다. 이름 절을 보십시오.

## 이름

**제품명, 권장: SpecSeal 을 유지하고, 안에서는 `seal` 한 단어를 어휘로
씁니다.**
루트 `seal/`, 명령 `seal export` / `seal import`, 기록을 가리키는 말 "the
seal" 입니다.

| 이름 | 한 문장으로 | 왜 아닌가 |
|---|---|---|
| SpecSeal | 스펙을 그것을 구현한 코드에 봉인한다 | — 무엇을 어떻게 하는지 말한다. "spec 은 빌려 온 말, seal 은 우리 것" 이 드러난다. spec-kit 과의 관계(그쪽이 쓰고, 우리가 봉인한다)가 읽힌다 |
| Seal | 봉인한다 | 목적어가 없어 순환한다. 충돌이 심하다(Microsoft SEAL, kubeseal). 마켓플레이스에서 찾을 수 없는 이름이다 |
| AiSeal | AI 가 만든 것을 봉인한다 | 봉인되는 것이 아니라 만든 이를 이름에 넣는다. 접두어가 낡는다. 충돌한다 |

복합 제품명 안에 한 단어 명령을 두는 것은 흔한 배치입니다(Sealed Secrets /
`kubeseal`). 이름을 바꾸면 저장소 URL, 마켓플레이스 항목, `plugin.json`,
훅 파일 접두어, 설치 문서, 그리고 태그 세 개 분량의 이력이 비용입니다.
언젠가 바꾼다면 0.4.0 이 가장 싼 순간입니다. 이 변경이 어차피 루트 이름을
바꾸기 때문입니다. 범위가 정말 "spec" 을 넘어설 때만 다시 보되, 그때도 seal
계열 안에서 고르고 AI 계열은 아닙니다.

**루트 이름, 권장: `.seal/` 이 아니라 보이는 `seal/`.** 점은 폴더의 성격에 대한
선언이지 동작 장치가 아닙니다. 옵트인이 로컬 설정에 있으면 훅은 어느 쪽이든
상관하지 않습니다. spec-kit 의 `specs/` 가 보이는 이유는 사람이 그 안의
것을 쓰고 읽기 때문입니다. 보존 기본값대로 릴리스 뒤에 사람의 기록을
남긴다면 그것은 문서 묶음이고, `docs/` 옆의 보이는 줄에 있어야 합니다.
`.seal/` 은 릴리스 때 작업 항목을 전부 비우고 흔적을 줄이는 것이 우선일
때만 고릅니다. 어느 쪽이든 나중에 바꾸는 비용은 디렉터리 이름 한 번입니다.

**하위 디렉터리 이름, 권장: `work/` 가 아니라 `seal/specs/<id>/`.** 처음
여는 사람이 디렉터리 이름만 보고 안에 무엇이 있는지 알 수 있어야 합니다.
`work` 로는 아무것도 알 수 없고, 비유(`forge/`)로는 내용이 가려집니다. smith 와 warden 은 에이전트
페르소나로 남습니다. 거기서는 이름이 성격을 말해도 되지만, 디렉터리 이름에는
쓰지 않습니다. `specs/` 는 핵심 산출물의 이름이고 제품명의 앞 절반이라,
트리를 보면 관계가 그대로 읽힙니다.

**배포되는 산출물은 전부 영어입니다.** 남에게 주는 플러그인이고 토큰마다
비용이 듭니다. 한국어는 소유자의 개인 설정입니다. 응답 언어와 `pr.ko.md`
가 그것입니다.

## 전환 시점에 기존 디렉터리는 어떻게 되는가

- **`specs/` 의 릴리스된 작업 항목.** 0.3.0 시점의 폴더는 전부 릴리스된
  작업 항목입니다. 이슈 본문은 옮기지 않고 지운다고 했습니다. 이력과
  CHANGELOG 주석이 보존하고, 라운드 기록의 `Target SHA` 는 전부 아직
  존재하는 커밋이기 때문입니다. 그런데 보존 기본값이 "사람의 기록은 남긴다"
  라면 전환 때도 같은 규칙을 적용하는 것이 일관됩니다. 사람의 파일은
  `seal/specs/<id>/` 로 옮기고 도구의 파일은 지우는 것입니다. 둘 중 무엇을
  택할지는 결정 사항입니다(아래).
- **전환 시점에 병합되지 않은 작업 항목**은 세션 시작 훅이 통째로 옮깁니다.
  `hooks/ledger-migrate.py` 가 이미 그 순간을 맡고 있습니다. 저장소마다 한
  번, 커밋 안 된 파일 위에서는 절대 돌지 않으며, 한 줄만 출력합니다. 지금의
  한 번 표시(`~/.claude/specseal/ledger-migrated`)는 앵커 형식 이관에 묶여
  있어서, 경로 이동에는 표시가 따로 필요합니다.
- **`.specseal/map.md` 와 `.specseal/map/`** 은 `seal/ledger.md` 와
  `seal/ledger/` 가 됩니다. `follow-up.md` 와 `parity.md` 는 그대로
  옮깁니다.
- 이 저장소에서는 그 뒤 `specs/` 가 비고 사라집니다.

## 바뀌지 않는 것

- 모든 게이트의 실패 방향은 그대로입니다. 판단할 수 없으면 옵트인하지 않은
  것으로 봅니다.
- 개발 중에는 작업 항목마다 조각을 두고 릴리스 때만 모으는 방식도
  그대로입니다. 병합 충돌을 없앤 것이 이것이고, 2026-09-01 에 병렬 브랜치
  셋이 그 덕을 봤습니다.
- `.git/` 의 세션 상태(smith 표시, 워크트리 선택, 세션 lease)는 그 자리에

- `docs/` 와 `CHANGELOG.md` 도, 정책서 > SDD > 코드라는 판단 순서도 그대로입니다.

## 순서

1. **이름 결정.** 플러그인 이름을 유지할지, 루트 이름, 하위 디렉터리 이름.
   여기서 사람이 정할 것은 이것뿐입니다.
2. **릴리스 자동화 작업 항목**이 "`ledger/` 를 합치고, 보존 규칙대로 작업
   항목을 비우고, 열린 evidence-todo 행이 있으면 거부한다" 를 맡습니다. 루트가
   병합되기 전에 지금 경로에서 할 수 있습니다.
3. **0.4.0, 루트 병합.** 세션 시작 훅이 한 번 이관합니다. CI 경로가
   바뀝니다. `docs/` 와 스킬의 경로 참조가 따라갑니다.
4. **나중에, 따로.** 상태를 작업 트리 밖으로 완전히 꺼냅니다. orphan
   브랜치를 대조표의 집으로 삼고 ref 로 옵트인하는 안이며, 이 이슈의 첫
   판본이 그것이었습니다.

## 범위 밖

- 개발 중인 작업 항목 안에서 사람의 파일과 도구의 파일을 가르는 일은 하지
  않습니다. 함께 옮깁니다. 이슈 본문은 이것을 아예 범위 밖에 두었고, 뒤의
  코멘트가 더한 보존 규칙은 둘을 가르기는 하지만 릴리스 때 지우는 것으로만
  가릅니다. 갈리는 자리는 그곳 하나이고, 그것을 정하는 자리가 결정 4 입니다.
