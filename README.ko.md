# SpecSeal

[![tests](https://github.com/MichaelYcJo/SpecSeal/actions/workflows/test.yml/badge.svg)](https://github.com/MichaelYcJo/SpecSeal/actions/workflows/test.yml)

[English](./README.md) · **한국어**

**Specs, sealed** — 스펙이 가리키는 코드가 바뀌면 CI 가 알려 줍니다.

![SpecSeal 데모: evidence-check 가 스펙-코드 드리프트를 잡는 모습](./assets/demo.gif)

코딩 에이전트는 다 됐다고 말합니다. SpecSeal 은 그 말이 열어 볼 수 있는 흔적을
남기게 합니다. 흔적은 셋입니다. smith 가 응답 끝에 적는 **증명 블록**(어떤 정책서를
읽었고 무엇을 실제로 실행했는지), 커밋 훅이 확인하는 **리뷰 표시**
(`.git/specseal-reviewed` 에 적히는, 리뷰를 마친 시점의 HEAD sha), 그리고 정책
조항마다 근거가 되는 코드 위치를 짝지어 둔 **근거 대조표**(`seal/ledger.md`)
입니다.

리뷰 표시 없이 커밋하면 훅이 커밋을 멈추고 어떻게 할지 물어봅니다. 대조표가
가리키는 줄을 건드리면 검사 스크립트가 실패로 끝납니다. 둘 다 벽은 아니고, 알고
지나가게 만드는 기록입니다.

Claude Code **플러그인**으로 배포됩니다. 근거 대조표와 드리프트 검사기, 인계 규약은
git 이 있는 곳이면 어디서든 동작합니다.

## 상시 컨텍스트가 12줄인 이유

도장은 작아야 도장입니다. [arxiv 2602.11988](https://arxiv.org/abs/2602.11988) 에
따르면 컨텍스트 파일은 대체로 성공률을 높이지 못하면서 추론 비용만 20% 넘게
늘립니다. 모델은 SOLID 도 DRY 도 이미 알고 있습니다. SpecSeal 은 기본 동작을
실제로 바꾸는 것만 싣습니다. 나머지는 부를 때 로드되는 스킬이거나, 컨텍스트
밖에서 도는 훅입니다.

## 무엇이 들어 있나

| 누구/무엇 | 따르는 스킬 | 실제로 무엇인가 |
|---|---|---|
| **smith** (Claude Code 서브에이전트) | `implement` · `writing-style` | 스펙에 맞춰 구현한 뒤 증명 블록 세 줄을 적는다. 어떤 정책서를 열었는지, 어떤 대조표 행을 고쳤는지, 무엇을 실행하고 무엇을 읽기만 했는지. 훅이 검사하는 것이 아니라 스킬이 요구하는 공개이며, `none — <이유>` 로 채워진 줄은 사용자 눈에 그대로 보인다 |
| **warden** (서브에이전트) | `code-review` · `writing-style` | 스펙 준수를 먼저 보고 그다음 품질을 본다. 보고서가 검증되면 오케스트레이터가 리뷰 시점의 HEAD sha 를 `.git/specseal-reviewed` 에 적고, 커밋 게이트는 그 파일을 확인한다. 리뷰어가 자기 표시를 직접 쓰지는 않는다 |
| **scribe** (서브에이전트) | `legacy-parity` | 원본 코드가 실제로 하는 일을 `경로#앵커` 좌표로 기록하고, 판정이 아니라 사실만 돌려준다. `seal/parity.md` 를 선언한 레포에서만 등장한다 |
| 스킬 | — | 스물한 개이고 세 묶음이다. 에이전트가 따르는 네 개는 왼쪽 열에 있다. 열한 개는 작업이 그것을 요구할 때 세션이 알아서 로드한다 — `audit`, `build-fix`, `checkpoint`, `commit-pr-convention`, `confidence-check`, `debug`, `evidence-check`, `feature-planner`, `gap-analysis`, `learn`, `verify`. 나머지 여섯은 사용자가 이름을 불러야 움직이며 아래 치트시트에 있다 |
| 훅 | — | 게이트 그 자체. 플러그인이 자동으로 등록하므로 설정을 따로 만질 필요가 없다 |
| CLAUDE.md 블록 | — | 늘 로드되는 12줄 — 절 제목 넷(`Tooling`·`Safety`·`Session cost`·`Git`)에 규칙 여덟이다. 툴링 하나, 안전 셋, 세션 비용 하나, git 셋. 응답 언어 규칙은 없다. 그것은 사용자 몫이다 |

## 체인

```
smith 가 만든다 → verify (좁게) → warden 이 리뷰한다 → 사용자에게 보고
      ↑                                                    │
      └──── 다시 만들기 ↔ 재리뷰, 1~n 회차 ───────────────┘
                          │ 회차 종결
                          ▼
             광역 관문 — 전 스위트·lint·타입체크, 한 번
                          │
        새로 깨진 것 → 순환으로 복귀 (세 번까지, 그다음은 멈춘다)
        base 에서도 실패 → follow-up 으로 이름 붙이고 막지 않는다
                          ▼
                       PR / 커밋
커밋   → .git/specseal-reviewed 가 HEAD 와 다르면 훅이 갈 수 있는 두 길을 띄운다
         — 리뷰를 돌리거나, [no-review] 를 붙여 커밋하거나
```

**광역 검사는 리뷰 회차가 끝난 뒤 한 번만 돕니다.** 증거는 트리 상태에 묶이므로,
회차 앞에서 찍은 전 스위트 봉인은 그 회차가 부르는 첫 수정에 깨집니다. 한 작업
항목에서 실측한 결과 광역 실행 스무 번이 **전부** 이후 편집을 동반했고, 핸드오프까지
살아남은 봉인은 하나도 없었으며, 그 값이 세션 도구 시간의 절반을 넘었습니다. smith 는
전 스위트를 `unverified` 로 표시해 넘깁니다. 범위를 좁히는 것이 정직할 수 있는 이유는
표시를 생략하지 않기 때문입니다. 관문에서는 결과를 base 커밋과 대조합니다. 작업보다
먼저 있던 실패는 쫓지 않고 follow-up 으로 이름을 붙이며, 그 봉인과 PR 사이에는
아무것도 편집하지 않습니다.

`verify` 는 smith 가 일을 넘기기 전에 스스로 거치는 관문입니다. 검사를 돌리고 출력을
끝까지 읽은 뒤, 주장마다 실행했는지·읽기만 했는지·확인하지 못했는지를 표시합니다.
warden 은 그 기록을 다시 돌리는 대신 감사합니다. 명령이 실제로 돌았는지, 그
검사가 실패할 수 있는 것인지, 표시가 정직한지를 봅니다. 결론을 그대로 받는 것과는
다르며, 코드는 그래도 직접 읽습니다. 나온 보고로 무엇을 할지는
사용자가 정합니다. 리뷰에는 상한이 있습니다 — **세 라운드. 머지를 막는 🔴 이 열려
있는 동안만 다섯까지 늘리고, 그것을 닫는 데에만 씁니다. 그다음엔 전부 해결됐든
아니든 끝납니다.** 다섯은 천장이지 목표가 아니라서, 마지막 🔴 이 닫히면 남은
라운드를 쓰지 않고 끝냅니다. 남은 것은 들고 가지 않고 넘깁니다. 답하지 못한 지적은
`seal/follow-up.md` 로, 사람만 정할 수 있는 결정은 `questions.md` 로, 원본의
동작이 명백히 잘못된 경우는 양쪽 텍스트를 나란히 기록해서 — 각각을 PR 본문에
이름 붙여 적습니다. **체인은 PR 에서 끝나며, 머지에서 끝나지 않습니다.** 보고에서
멈추면 끝난 일이 아무도 찾지 않는 곳에 남고, 머지하면 체인의 몫이 아닌 결정을 한
것입니다. 그 PR 을 머지할지, 한 라운드 더 돌릴지, 닫을지는 사용자의 몫입니다.

**warden 은 아무것도 모르는 상태에서 시작합니다.** 서브에이전트로 뜨므로 구현
대화가 닿지 않고, 넘어가는 것은 글로 적힌 것뿐입니다. diff 와 스펙, 그리고
작업 항목에 남은 라운드 기록입니다. 유일한 통로는 warden 을 띄우는 프롬프트라서,
거기에 구현 근거가 실려 있으면 warden 은 그것을 증거가 아니라 작성자의 주장으로
다루고 제쳐 두었다는 사실을 보고에 적습니다. 통로 자체를 없애려면 새 세션을 열어
거기서 `@agent-specseal:warden` 을 부르면 됩니다. 회차 이력은 파일이라 어느
쪽이든 그대로 이어집니다.

## 저장소에 남는 기억

세션이 끝나도 남아야 하는 것은 세션이 아니라 저장소에 적습니다.

| 루트 | 수명 | 담는 것 |
|---|---|---|
| `seal/` | 영구 | 이 플러그인이 유지하는 전부 — 대조표, follow-up 목록, 저장소 자신의 설정(언어 두 행과 모드가 여기 있다), 이관 설정 — 와 그 아래의 작업 항목들. 이 디렉터리가 있다는 것 자체가 옵트인이며, 이것을 보는 훅은 넷이다 — 커밋 게이트, 리뷰 스킬 게이트, 리뷰 이력 가드, 버전 확인. worktree-guard 와 session-lease 는 git 레포면 어디서든 돌고, lint-python 은 ruff 설정을 따른다(아래 Where 열 참조) |
| `seal/specs/<id>/` | 작업 항목 하나 | SDD 세트 — spec, plan, questions, 그리고 diff 가 보여 주지 못하는 것만 적는 마무리 메모. `plan.md` 는 사람이 승인하므로 도구 상태가 아니라 레포의 문서다 |
| `docs/` | 영구 | 레포가 원래 갖고 있는 정책서. **여기서 만들지 않는다** — 문서 관례는 그 프로젝트의 것이다 |

```
seal/
├── README.md         인계 규칙 — 작업 항목을 닫기 전에 무엇을 어디로 옮기는지
├── ledger.md         조항 ↔ 코드 좌표. 작업 항목별 파일이 생기기 전에 쌓인 것
├── ledger/
│   └── <작업항목-id>.md   그 작업 항목의 행. 머리글이 없고, 릴리스 때 ledger.md 로 합친다
├── config.md         이 저장소가 자기에 대해 말하는 것. 언어 두 행과 모드.
│                     선택이고, 행이 없는 것은 오류가 아니다
├── parity.md         이관 설정, 선언했을 때만
├── follow-up.md      추적기가 없는 레포에서 일정을 잡을 수 있는 항목
└── specs/<작업항목-id>/
    ├── routing.md    이 작업을 어느 길로 보낼지, 첫 수정 전에 적는다
    ├── spec.md · plan.md · questions.md · overview.md
    ├── rounds/
    │   └── round-N.md    리뷰 회차 — 커밋해 두었다가 다 옮기고 나면 닫고 남긴다
    └── tests-todo.md · evidence-todo.md
```

판단 순서는 정책서가 있는 레포에서는 정책서 > SDD > 코드이고, 없으면 SDD >
코드입니다. 대부분의 레포가 후자이며, 플러그인이 전자를 만들어 내지 않습니다.

없는 파일은 `templates/` 에서 만들어집니다. 인계 규약은
[docs/review-handoff-protocol.md](./docs/review-handoff-protocol.md) 에 특정
도구를 전제하지 않고 적혀 있습니다. git 레포의 파일을 읽고 쓸 수 있는
에이전트라면 무엇이든 그대로 따를 수 있습니다. 규약이 말하는 자리는 **작업
항목이 사는 디렉터리 옆**이고, `seal/specs/<id>/` 는 이 저장소가 그 자리를 어디로
잡았는지일 뿐 규약 자체는 아닙니다.

대조표는 쌓아 두기만 하는 것이 아니라 **검사**받습니다. 좌표는 파일 안의 **위치가
아니라 내용**을 가리킵니다. 형태는 `경로#단위@해시` 이고, 단위는 코드면 함수나
클래스, 문서면 제목입니다. 해시는 그 단위가 덮는 구간의 내용을 줄인 값입니다.
주장이 함수 안의 특정 문장에 걸려 있으면 `>` 뒤에 그 문장을 덧붙여 범위를 좁힐 수
있습니다.

`evidence-check` 스킬의 CI 스크립트는 앵커가 사라졌거나 여러 곳에서 걸리면 2 로,
앵커 아래 내용이 바뀌었으면 1 로 끝납니다. 기본 CI 설정에서는 둘 다 실패로 잡히고,
`--strict` 를 주면 드리프트도 2 가 됩니다. 이 검사가 증명하는 범위는 좁습니다.
인용한 자리가 아직 그 내용을 담고 있다는 것이지, 그 자리가 뒷받침하는 주장이
여전히 맞다는 뜻은 아닙니다. 다른 곳에서는 스펙이 조용히 낡아 가지만, 여기서는
낡는 순간 CI 에 드러납니다.

**행에는 줄 번호도 커밋도 적지 않습니다.** 줄 번호는 그 주장과 아무 상관 없는
수정에도 밀립니다. 그래서 인용한 함수 위에 한 줄을 끼워 넣으면 행이 엉뚱한 줄을
가리키면서도 통과로 읽혔습니다. 앵커는 밀리지 않으므로 그런 수정에는 아무 말도
하지 않고, 인용한 코드가 실제로 바뀌었을 때만 알려 줍니다. 리베이스나 스쿼시가
끊어 놓을 값이 행 안에 없고, 검사는 git 을 부르지 않습니다. 예외는 `--migrate`
하나뿐입니다. 낡은 형식을 한 번에 고쳐 쓰는 명령이라, 줄 번호를 믿기 전에 그
번호가 적힌 시점의 커밋을 확인합니다.

**앵커는 못 찾겠다가 아니라 바뀌었다로 무너집니다.** 좁혀 둔 문장이 없어져도
BROKEN 이 아니라 그 단위 전체를 놓고 DRIFTED 로 알려 줍니다. BROKEN 은 대조표를
고치러 가라는 뜻이고, 그 손질이 바로 이번 변경이 없애려는 일이기 때문입니다.

행을 다시
확인하는 일은 코드를 다시 읽은 뒤 `evidence-check --reverify` 를 돌리는 것입니다.
바뀐 해시를 다시 계산하고 무엇을 고쳤는지 이름을 찍어 줍니다.

## 게이트

훅은 플러그인이 자동으로 등록하는 스크립트이며, 도구를 호출하는 시점에
사용자 컴퓨터에서 실행됩니다. 한 이벤트에 걸린 게이트들은 게이트마다 하나씩이
아니라 프로세스 하나가 묶어서 처리합니다 — Bash 호출 한 번에 파이썬을 네 번
띄우는 것이 게이트를 두는 비용의 대부분이었습니다(실측: Bash 호출 전 220ms →
104ms, 후 323ms → 120ms). 판정표 전문은 다음 두 문서에 있습니다.
[docs/worktree-guard-spec.md](./docs/worktree-guard-spec.md) ·
[docs/review-chain-spec.md](./docs/review-chain-spec.md)

| 게이트 | 언제 | 무엇을 | 어디서 |
|---|---|---|---|
| commit-review-gate | `git commit` 직전 | `.git/specseal-reviewed` 가 현재 HEAD 와 다르면 커밋을 세우고, 갈 수 있는 두 길을 선택지로 띄운다 — 리뷰 체인을 돌리거나, `[no-review]` 를 붙여 커밋하거나(그 표시는 명령에 그대로 남는다). `seal/parity.md` 를 선언한 레포에서는 코드를 커밋할 때 이번 HEAD 의 `.git/specseal-parity` 가 없으면 같은 방식으로 원본 대조와 `[no-parity]` 를 함께 묻는다. 둘 다 걸리면 질문 두 개를 한 번에 낸다. **세션·레포당 한 번**만 이렇게 묻고, 그 다음부터는 승인이 곧 면제인 일반 확인창이다. 판정 대상은 셸이 있는 레포가 아니라 **커밋이 들어가는** 레포다 — `git -C <경로> commit` 은 `<경로>` 기준으로 본다. `-C` 값이 레포로 풀리지 않으면(게이트는 셸이 확장하기 전의 명령을 보므로 셸 변수가 그대로 온다) 통과시키지 않고 커밋을 세운다. 아무것도 안 본 것인데, 그동안은 보고 통과시킨 것과 구분되지 않았다 | 루트에 `seal/` 이 있는 레포, 또는 local 모드로 공통 git 디렉터리 아래에 있는 레포. 그 밖에서는 아무것도 하지 않는다. 이관 설정은 그 디렉터리 안에 있으므로 그것을 선언하면 두 팔 다 켜진다 — 리뷰 쪽만 빼려면 명령 **앞에** `[no-review]` 를 붙인다. 따옴표까지 그대로 `: '[no-review]'; git commit …` 이고, `git commit` 뒤에 쓰면 git 이 경로 인자로 읽어 거부한다 |
| review-history-guard | `gh` 로 PR 리뷰 게시/조회 직후 | `seal/specs/<작업항목>/rounds/round-N.md` 와 `rounds/` 옆의 todo 파일 둘에 쓰거나 읽으라고 알린다. 예전 자리에 그대로 남은 기록이 있으면 그 파일 이름도 함께 알린다 — 거기 있는 것은 아무도 읽지 않는다. 어느 작업 항목인지는 커밋 게이트와 같은 방식으로 찾는다 — 이 브랜치를 적어 둔 라우팅 선언. 그래서 선언이 없는 브랜치에는 알리지 않는다 | 위와 같은 옵트인 |
| review-skill-gate | 모델이 `code-review` 라는 이름의 스킬을 열기 직전 | 고르지 않고 사용자에게 고르게 한다. 그 이름은 Claude Code 내장이지 이 플러그인 것이 아니다. 내장은 diff 에서 버그와 중복을 훑고, `specseal:code-review` 는 스펙 준수를 먼저 본 뒤 이전 회차 판정을 이어받는다. **세션·작업트리당 한 번**만 물으므로, 내장을 골라 다시 부르면 그대로 통과한다. 사용자가 직접 부른 스킬은 여기를 거치지 않는다 | 루트에 `seal/` 이 있는 레포, 또는 local 모드로 공통 git 디렉터리 아래에 있는 레포. 그 밖에서는 아무것도 하지 않는다 |
| worktree-guard | `git checkout`·`switch`·`worktree add` 와 `isolation: "worktree"` 로 부른 Agent 직전 | 한 규칙의 두 방향이다. 다른 세션이 이 트리에서 작업 중이면 전환을 막고, 반대로 혼자 작업 중이면 worktree 생성을 막는다. 멈춘 세션뿐이거나 판정 자체가 불가능한 환경에서는 갈 수 있는 두 길을 선택지로 띄운다 — 이 트리에서 전환하거나, worktree 로 분리하거나. **세션·레포·방향당 한 번**만 이렇게 묻고 그 다음부터는 일반 확인창이며, 고른 답은 `[worktree-ok]` 와 `[shared-tree-ok]` 가 재시도 때 그대로 실어 나른다. 두 방향을 따로 세므로 한 세션이 이 질문을 두 번 만나는 것은 정상이다. 사유에는 상대 세션의 호스트 앱, 신호별 경과 시간, 마지막 메시지가 함께 나온다 | 모든 git 레포 |
| session-lease | 저장소를 건드리는 도구 호출(Bash·파일 편집) 직후 | `.git/specseal-leases/<세션id>` 에 시각·호스트·세션 pid 를 적는다. 프로세스 이름이 `claude` 가 아닌 세션은 가드가 놓치는데, lease 는 어느 세션이 여기서 일하는지 그냥 밝혀 준다. 세션이 끝나도 파일은 지워지지 않으므로 주인을 함께 적는다. 끝난 세션의 lease 는 세지 않고 버리며, 주인을 확인할 수 없는 lease 는 차단이 아니라 질문이 된다 | 모든 git 레포 |
| version-check | 세션 시작 시 | 이 저장소에 최신 릴리스 태그를 물어보고, 실행 중인 플러그인이 뒤처져 있으면 `/specseal:update` 를 알린다. 하루 한 번 물어보고, 조회가 실패하면 20분쯤 뒤에 다시 시도한다. 설치는 하지 않는다. 릴리스가 있다고 알리는 것과 남의 기계에 설치하는 것은 다른 일이다 | 루트에 `seal/` 이 있는 레포, 또는 local 모드로 공통 git 디렉터리 아래에 있는 레포. 그 밖에서는 아무것도 하지 않는다 |
| lint-python | `.py` 파일을 Write·Edit·NotebookEdit 한 직후 | 그 파일에 `ruff check --fix` 를 돌린 뒤 `ruff format` 을 돌린다. 자동수정이 포함되므로 레이아웃만이 아니라 코드가 바뀐다 (uv → uvx → 전역 순으로 찾고, 없으면 건너뛴다). `SPECSEAL_LINT=off` 로 끌 수 있다 | **ruff 를 설정한 프로젝트** — `ruff.toml`, `.ruff.toml`, 또는 `pyproject.toml` 의 `[tool.ruff]`. 레포 루트까지 거슬러 찾는다. 그 밖에서는 아무것도 하지 않는다 |

리뷰 체인을 강제하는 자리는 이제 커밋만이 아니고, 갈 길을 선언한 작업 항목에서는
커밋이 아예 그 자리가 아닙니다. 작업 항목은 첫 수정 전에 `seal/specs/<id>/routing.md`
를 씁니다 — 어느 길로 갈지, PR 을 열지. 게이트는 리뷰 표시가 없다는 사실로
되짚는 대신 그 파일을 읽습니다. 검사는 PR 로 옮겨 갔습니다. CI 가 diff 에서 같은
파일을 읽고, 리뷰 체인으로 간다고 적힌 것에 대해서는 커밋된 라운드 기록을
요구합니다. 그 기록의 `Pass` 표시가 자기 판정표와 어긋나면 막습니다. 어느 쪽도
선언하지 않은 PR 은 실패시키지 않고, **아무것도 검사하지 못했다**는 알림만
남깁니다.

라운드 기록에는 **그 회차가 찾아낸 것을 닫은 수정을 누가 열어 봤는지**도
적습니다. 한 회차의 지적은 그 회차가 끝난 뒤에 수정으로 닫히고, 그 수정을 읽는
것은 다음 회차입니다. 마지막 회차만 예외였습니다 — 아무도 읽지 않았고, 리뷰가
통과했다는 표시는 그 수정을 방금 쓴 세션이 직접 찍었습니다.

그래서 리뷰는 **검증 회차**로 끝납니다. 앞 회차의 수정이 커밋된 뒤에 띄우고,
브랜치가 아니라 그 수정의 diff 를 대상으로 삼아, 닫혔다고 적힌 지적이 실제로
닫혔는지만 봅니다. 수정이 필요한 것을 하나도 열지 않은 회차는 3회 한도를 쓰지
않습니다.

그 결과가 들어가는 자리가 `Fixes checked by` 행입니다. 뒤 회차 이름을 적거나,
확인할 수정이 없었다고 적거나, `nobody` 와 그 이유를 적습니다. 마지막 값은 매
실행마다 출력되고, 마지막 회차 기록에서 `Pass` 옆에 적혀 있으면 PR 을 깨뜨립니다.
이 규칙 이전에 시작된 작업 항목은 제외되고 출력만 됩니다.

어떤 게이트도 사용자의 코드나 경로, 프롬프트를 바깥으로 보내지 않습니다. 다만
세 가지 부수 효과는 밝혀 둡니다. session-lease 는 `.git/specseal-leases/` 아래에,
version-check 는 `~/.claude/specseal/` 아래에 시각 파일을 쓰고, lint-python 은
방금 저장한 `.py` 파일을 고쳐 씁니다 — ruff 를 설정한 프로젝트에서만입니다.

네트워크를 타는 훅은 둘입니다. lint-python 은 `uvx ruff` 로 넘어갈 때 uv 가 처음
한 번 PyPI 에서 ruff 를 내려받습니다. version-check 는 이 저장소에 `git ls-remote
--tags` 를 한 번 보냅니다. `seal/` 이 있는 곳에서 하루 한 번 돌고, 조회가
실패하면 하루를 기다리지 않고 20분쯤 뒤에 다시 시도합니다. 이때 GitHub 이 알게
되는 것은 어딘가의 기계가 SpecSeal 을 쓴다는 사실입니다.
둘 다 네트워크가 없으면 조용히 넘어갑니다.

일부러 읽는 것도 하나 있습니다. worktree-guard 가 브랜치 전환을 막을 때, 지금
무엇을 보호하는지 사람이 알아볼 수 있게 다른 세션 기록에서 마지막 사용자 메시지
80자를 가져옵니다.
이 조각은 차단 사유에만 쓰이고 기기 밖으로 나가지 않습니다.

## 원본을 기준으로 삼기 (마이그레이션)

`seal/parity.md` 에 원본 저장소와 기준 커밋을 적어 두면 3자 판정을 쓸 수
있습니다. 정책서와 원본, 신규 코드를 나란히 놓고 판정하며, 판단이 갈리면
**원본을 보존하는 쪽**이 기본값입니다. 이때 scribe 가 원본이 실제로 어떻게
동작하는지 확인해 옵니다. 이 파일이 없는 레포에서는 이 기능이 아예
나타나지 않습니다.

이 파일을 직접 쓸 일은 없습니다. smith 가 그 레포의 문서 구조를 처음 만들 때 한 번
물어봅니다 — *이 프로젝트는 기존 코드베이스의 동작을 옮겨 오는 작업입니까?* 아니라고
답하면 다시 묻지 않습니다. 맞다고 답하면 원본 후보를 찾아 제시하고(옆에 체크아웃된
레포, `git remote -v` 의 upstream, 경로 구조가 겹치는 레포), 확인해 준 쪽의 HEAD 를
읽어 기준 커밋으로 적은 뒤 파일을 만듭니다. 나중에 결정하는 경우에는
`/specseal:parity-setup` 을 실행하면 됩니다.

체크아웃 경로는 커밋되는 파일에 들어가지 않고 `~/.claude/specseal/parity-paths.md` 에
origin remote 를 키로 저장됩니다. 다른 기계에서는 틀린 값이기 때문입니다.

**명령에 섞는 스위치:**

| 스위치 | 효과 |
|---|---|
| 커밋 명령의 `[no-review]` | **그 명령 하나만** 리뷰 게이트를 건너뛴다. 명령에 그대로 남아 흔적이 된다. 명령 **앞에** 붙인다 — 따옴표까지 그대로 `: '[no-review]'; git commit …`. `git commit` 뒤에 쓰면 git 이 경로 인자로 읽어 명령 전체를 거부한다. 뒤에 `# [no-review]` 를 다는 형태는 대화형 zsh 에서만 깨지는데, 거기서는 `#` 이 주석이 아니라서 `[no-review]` 가 매칭 없는 glob 이 된다 |
| 커밋 명령의 `[no-parity]` | **그 명령 하나만** 원본 대조 게이트를 건너뛴다. 마찬가지로 흔적이 남고, 붙이는 자리도 같다 — `: '[no-parity]'; git commit …` |
| worktree 명령의 `[worktree-ok]` | 혼자 작업할 때 worktree 생성을 막던 것을 확인창으로 완화한다. 명령의 낱말로 있을 때만 세므로 따옴표 안의 문장에 적힌 것은 세지 않는다. `isolation: "worktree"` 로 부르는 Agent 는 명령줄이 없어 토큰을 받지 않고, 대신 바로 확인창을 띄운다 |
| 전환 명령의 `[shared-tree-ok]` | 공용 트리에서 전환하기로 이미 골랐다는 표시다. 가드가 판정하지 못하는 자리(멈춘 세션뿐, 환경 조회 불가)에서 전환이 그대로 통과한다. 명령의 낱말로 있을 때만 센다. 다른 세션이 작업 중일 때와 트리가 더러울 때는 무시된다 |
| `WORKTREE_GUARD_IDLE_MIN=n` | 세션을 멈춘 것으로 볼 기준 시간, 분 단위 (기본 5) |
| `SPECSEAL_LINT=off` | ruff 를 설정한 곳에서도 파이썬 자동 포맷 훅을 끈다 |
| `SPECSEAL_LANG=ko\|en` | worktree-guard 문구의 언어 (나머지 게이트는 영어만 나옵니다). 기본은 시스템 로케일을 따릅니다 |

## 설치

**요구사항**은 `git` 과 **Python 3.12 이상**입니다. 게이트가 파이썬
스크립트이고 플러그인은 이를 `python3` 명령으로 실행하므로, 그 이름이 3.12
이상을 가리켜야 합니다. 당연하게 여기지 말고 한 번 확인하시는 편이 좋습니다 —
macOS 의 `/usr/bin/python3` 은 3.9 이고, 버전 매니저(pyenv, asdf)를 쓰면
`python3` 은 마지막으로 지정한 버전을 가리킵니다. `python3 -V` 하나로 끝납니다.
Windows 는 공식 설치본이 `python3` 이라는 이름을 만들지 않으므로, 훅마다
`python3` 이 실행되지 않으면 `py -3` 으로 한 번 더 시도합니다. `uv`/`uvx` 나
`ruff` 는 파이썬 자동 포맷 훅에만 쓰이고, 없으면 그 훅만 건너뜁니다.

```bash
# 1. 플러그인 (에이전트 + 스킬 + 게이트)
claude
> /plugin marketplace add MichaelYcJo/SpecSeal
> /plugin install specseal@specseal

# 2. CLAUDE.md 블록 — 범위는 하나만 선택
bash install.sh            # 대화형: 전역(~/.claude) 또는 프로젝트(./)
bash install.sh --project  # 비대화형 프로젝트 범위
```

### 업데이트

```
/specseal:update
```

아래 두 명령을 순서대로 돌린 뒤, 쓰던 버전과 새 버전 사이의 변경 항목을 알려
줍니다. 동작이 바뀌는 것과 사용자가 할 일이 있는 것은 따로 짚어 줍니다. 적용은
재시작 후이고, 지금 세션은 시작할 때의 버전을 그대로 유지하므로 반쯤 적용되는
일은 없습니다.

직접 하려면 이렇습니다.

```bash
claude plugin marketplace update specseal
claude plugin update specseal@specseal   # 그다음 재시작
```

두 줄을 이 순서로 실행합니다. 첫 줄이 마켓플레이스 클론을 갱신하고, 둘째 줄이
거기서 설치합니다. 둘째 줄만 실행하면 클론이 마지막으로 알던 정보를 보고 *이미
최신*이라고 답합니다. 업데이트는 커밋이 아니라 `plugin.json` 의 버전을
기준으로 하므로, 버전을 올리지 않고 내보낸 변경은 아무에게도 도달하지 않습니다.

`install.sh` 는 기존 파일을 `CLAUDE.md.bak` 으로 백업한 뒤 자기 마커 블록만
병합합니다. 여러 번 실행해도 결과가 같고, 다시 실행하면 블록만 갱신됩니다.
사용자가 직접 쓴 내용은 고치지 않으며, 겹치는 부분이 있으면 경고만 남긴 채
그대로 둡니다. 중복까지 정리하려면 Claude Code 안에서
`/specseal:preset-setup` 을 실행하세요. 무엇을 지우든 diff 를 보여 주고
승인을 받습니다.

### 0.3.x 에서 올라오는 경우

0.3.x 는 플러그인 파일을 두 디렉터리(`.specseal/`, `specs/<id>/`)에 두었고,
이번 릴리스는 `seal/` 하나에 둡니다. 이제는 이 폴더가 있다는 것이 옵트인입니다.
옛 두 디렉터리는 더 이상 아무것도 켜지 않으므로, 옮기기 전까지는 그 레포에서
모든 게이트가 침묵합니다.

옮기는 일은 업데이트 뒤 첫 세션 시작 때 한 번 일어납니다. 훅이 파일마다
`git mv` 로 스테이징된 이름 바꾸기를 하고(이력이 따라옵니다), 옮겨진 파일을
가리키는 대조표 행의 경로를 해시는 건드리지 않은 채 고쳐 쓰고, 무엇을 옮겼는지
한 줄 알린 뒤 멈춥니다. 그다음은 사용자 몫입니다. `git diff --cached` 를 보고
커밋하면 됩니다. 이 커밋은 어느 작업 항목에도 속하지 않아 세션 안에서는
커밋 게이트가 묻습니다. 그 명령 하나만 면제하려면
`: '[no-review]'; git commit -m "specseal: the root move"` 로 커밋하고,
`seal/parity.md` 가 있으면 같은 자리에 `[no-parity]` 도 붙입니다.

옛 두 디렉터리 아래에 커밋하지 않은 변경이 있으면 먼저 커밋하라는 한 줄만
남기고 옮기지 않으며, 다음에 깨끗한 상태로 세션을 시작하면 그때 옮깁니다.
일회용 표시 `.specseal/scratch` 가 있는 레포는 그대로 둡니다. 그 표시의
후임은 커밋될 수 없는 파일 `.git/specseal-scratch` 입니다.

CI 에서, 또는 다음 세션을 기다리지 않고 직접 옮기려면 이렇게 합니다.

```bash
mkdir -p seal/specs
git mv .specseal/map.md seal/ledger.md
git mv .specseal/map seal/ledger             # 있을 때만
git mv .specseal/README.md seal/README.md    # 그다음 templates/seal-README.md 로 덮어쓴다
git mv .specseal/follow-up.md seal/          # parity.md 와 그 안의 나머지도 같이
git mv specs/<id> seal/specs/<id>            # 작업 항목마다
rmdir .specseal specs                        # git mv 는 빈 디렉터리를 디스크에 남긴다. 다른 것이 든 쪽은 남는다
evidence-check --reverify .                  # 옮겨진 파일을 가리키는 행을 고쳐 써 준다
```

## 처음 실행

게이트 일곱 중 넷은 조건이 맞아야 깨어납니다. 커밋 게이트와 리뷰 이력 알림,
리뷰 스킬 게이트, 버전 확인은 레포 루트에, 또는 그 레포의 git 디렉터리 아래에
`seal/` 디렉터리가 있을 때만 동작하고, 그 전까지는 침묵합니다. 이 디렉터리를
직접 만들 일은 없습니다. smith 가 그 레포에서 처음 일할 때 질문 하나(아래
「shared 인가 local 인가」)를 하고 만들며, 이 플러그인이 사용자 트리에 추가하는
디렉터리는 이것 하나뿐입니다. shared 모드에서는 `.github/workflows/` 아래
워크플로 파일 하나가 더 들어가고, local 모드면 트리에는 아무것도 추가하지
않습니다.

나머지 셋은 각자의 조건이 있습니다. worktree-guard 와 session-lease 는 모든 git
레포에서 돕니다. lint-python 은 프로젝트가 ruff 를 설정한 곳에서만 돕니다 —
ruff 를 설정한다는 것이 그 프로젝트가 ruff 를 원한다는 뜻이고, 그 밖에는 그런
선언이 없습니다. 전역으로
설치하기 전에 위 표의 "어디서" 열을 먼저 보세요.

에이전트는 이름을 불러야 움직입니다.

```
> @agent-specseal:smith <티켓> 구현해줘
```

`@agent-` 를 치면 이름을 채워 주는 목록이 뜹니다. 문장으로 풀어 써도 똑같이
동작하므로 이쪽이 편하면 그대로 쓰면 됩니다.

```
> specseal:smith 에이전트로 <티켓> 구현해줘
```

smith 는 스펙 체인을 읽고 구현한 뒤 검증까지 마치고, 리뷰는 warden 에게
넘깁니다. 나온 리포트를 어떻게 할지는 사용자가 정합니다. 고칠 수도, 다시
리뷰를 돌릴 수도, 그대로 커밋할 수도 있습니다.

문서 구조에 필요한데 레포에 없는 것은 smith 가 작업하면서 `templates/` 에서
만듭니다. `seal/ledger.md` 와, 인계 규칙을 담은 `seal/README.md` 가
그렇습니다. 작업하면서 새로 적는 행은 `seal/ledger/<작업항목-id>.md` 로
갑니다.

에이전트를 쓰지 않아도 되는 기능이 두 가지 있습니다. 앞의 데모에서 보여 준
대조표 검사(`evidence_check.py`)와, 위 표에 적은 게이트 전부입니다.

### shared 인가 local 인가

smith 가 어떤 저장소에서 처음 일할 때 질문을 하나 합니다. 한 번뿐이고 다시
묻지 않습니다. `seal/` 을 어디에 둘 것인가입니다. 폴더가 있는 자리가 곧
모드이고, 설정 키는 없으며, 두 자리 중 어디든 `seal/` 이 있는 저장소에는
묻지 않습니다.

| | shared (기본값) | local |
|---|---|---|
| `seal/` 이 사는 자리 | `<repo>/seal/`. 커밋한다 | `$(git rev-parse --git-common-dir)/seal/`. 공통 git 디렉터리 아래로, 메인 트리에서는 `.git/` 이다 |
| 설정이 설치하는 것 | PR 검사. 플러그인의 `templates/hygiene.yml` 에서 `.github/workflows/hygiene.yml` 로, 그 자리가 비어 있을 때만 | 아무것도. 트리에는 손대지 않는다 |
| 맞는 곳 | 자기 저장소, 또는 `seal/` 이 커밋돼도 아무에게도 지장이 없는 저장소 | 이 플러그인의 파일이 트리에 있으면 안 되는 저장소. 회사 저장소, 남의 프로젝트에 기여할 때 |
| 포기하는 것 | 없다 | CI(검사가 커밋된 파일을 읽는다)와, 비어 있는 채로 시작하는 다른 기계나 재클론 |

local 모드가 `.gitignore` 줄이 아니라 git 디렉터리 아래에 있는 이유는,
연결된 워크트리가 커밋된 파일만 체크아웃하기 때문입니다. 무시한 폴더는
거기서 그냥 없습니다. 공통 git 디렉터리는 그 클론의 모든 워크트리가
공유하고, 그 아래의 것은 커밋 후보가 되지 않습니다.

**바꾸는 것은 명령 하나입니다.** 명령은 스테이지까지만 하고, 커밋은
직접 합니다.

```bash
seal mode            # 루트가 어디 있는지, 설정이 뭐라고 하는지, 둘이 맞는지
seal mode local      # 트리 밖으로 옮긴다
seal mode shared     # 트리 안으로 옮긴다
```

옮기는 일 자체는 아래에 적어 둔 셸 두 줄입니다. 명령이 더 하는 것은 그
주변입니다. 다른 쪽 모드의 루트가 이미 있으면 거부하고, 루트 아래에
서브모듈이 있으면 거부하고, `seal/` 아래나 워크플로 파일 자리에 인덱스가
들고 있는 변경이 있으면 거부합니다. `git rm -r --cached` 는 스테이지해 둔
수정을 인덱스에서 아무 말 없이 빼 가기 때문입니다. 그리고
`.github/workflows/hygiene.yml` 을 할 수 있는 한 함께 넣고 빼며, 못 하면
그렇다고 말합니다. `seal/config.md` 에 모드를 적어 두어 파일과 폴더가
그다음부터 같은 말을 하게 합니다. 훅을 다시 띄울
필요는 없습니다. 다음 명령이 폴더가 있는 자리를 그대로 읽습니다.

**설정의 줄은 원하는 것이고, 폴더의 자리는 실제입니다.** 실행 중에 그 줄을
읽는 것은 아무것도 없습니다. 모든 게이트는 위의 두 자리를 찾아보는 것으로
루트를 정합니다. 그래서 둘은 어긋날 수 있고, 그것은 오류가 아니라 이 명령이
받아먹는 입력입니다.

```bash
# seal/config.md 를 `| Mode | local |` 로 고친 다음
seal mode --apply    # 줄이 말하는 자리로 폴더를 옮긴다
seal mode --check    # 아무것도 쓰지 않고, 어긋나 있으면 0 이 아닌 값으로 끝난다
```

`--check` 는 PR 검사가 돌리는 것입니다. 사실이 아니게 된 줄이 그대로 남아
있으면 거기서 걸립니다. 한 번도 선언한 적 없는 저장소는 아무 거짓말도 하고
있지 않습니다. 처음 `seal mode` 를 돌리면 폴더가 실제로 있는 자리를 보고 그
줄을 써 줍니다.

**두 방향의 값이 같지 않습니다.** local 로 가면 기록이 트리에서 빠지고,
다른 클론은 다음 pull 에서 그것을 잃습니다. 여기서 `seal export`, 저기서
`seal import` 가 동료가 사본을 받는 길입니다. 확실히 하고 넘어가야 하는
쪽은 shared 입니다. 커밋하고 나면 기록이 히스토리에 들어가고, 나중에 트리
에서 빼도 히스토리에서는 빠지지 않습니다. 그 커밋 전까지는
`git reset -- :/seal :/.github/workflows/hygiene.yml` 뒤에 `seal mode local` 이
전부 되돌립니다. 스위치가 스테이징을 하고 가드는 스테이징된 변경 위에서의
전환을 거부하기 때문입니다. 경로를 적는 이유는 그냥 `git reset` 이 인덱스
전체를 풀어 버리는데, 이 가드는 저 두 경로 밖을 본 적이 없어서입니다.

손으로 하면 저장소 루트에서 옮기고 커밋하는 일입니다. 두 경로 모두 git 에
물어서 얻으므로, 하위 디렉터리에서 실행해도 같은 자리에 놓입니다.

```bash
# local → shared, 그다음 커밋
mv "$(git rev-parse --git-common-dir)/seal" "$(git rev-parse --show-toplevel)/seal" && git add "$(git rev-parse --show-toplevel)/seal"
# shared → local, 그다음 지운 것을 커밋
git rm -r --cached "$(git rev-parse --show-toplevel)/seal" && mv "$(git rev-parse --show-toplevel)/seal" "$(git rev-parse --git-common-dir)/seal"
```

그렇게 하면 워크플로 파일이 그 자리에 남고, 그것이 알아 둘 만한 나머지
절반입니다. `$CLAUDE_PLUGIN_ROOT/templates/hygiene.yml` 을 복사해 넣거나
(`v<version>` 은 쓰는 릴리스로 바꿔서), `.github/workflows/hygiene.yml` 을
지웁니다. local 로 옮긴 뒤 그대로 두면, 커밋된 파일을 읽는 검사가 아무것도
커밋하지 않는 저장소에서 계속 돕니다. 하나는 모든 PR 에서 영영 빨간불이 되고,
다른 하나는 아무것도 읽지 않은 채 초록불이 됩니다.

기계가 둘이면 이 방법을 쓸 수 없습니다. 다른 기계에는 옮길 폴더 자체가
없기 때문입니다. 아래의 `seal export` 와 `seal import` 가 그것을 위한
것이고, 모드를 바꾸는 두 번째 방법이기도 합니다.

### local 의 기록을 다른 기계로 가져가기

local 모드가 감수하는 것은 기록이 그 클론을 벗어나지 않는다는 점입니다.
`seal export` 와 `seal import` 는 그것을 *잃는다* 가 아니라 *복사본을
가져간다* 로 바꿔 줍니다. 플러그인이 켜져 있는 동안 두 명령 모두 그냥
칠 수 있습니다.

```bash
seal export                 # 클론 옆에 seal-<repo>-<date>.zip 을 씁니다
seal import <그 zip>        # 받아 들이되, 아무것도 덮어쓰지 않습니다
```

zip 에는 루트만 들어갑니다. smith 표식, 워크트리 선택, 리뷰·parity 표식,
리스 파일은 모두 루트 *옆* 의 git 디렉터리에 있어서 따라가지 않습니다.
export 가 루트만 걸어서 그렇고, 루트가 자기 디렉터리여야 하는 이유가
이것입니다. 루트 안의 심볼릭 링크는 따라가지 않고 건너뛴 뒤 이름을
알려 줍니다. 파일들과 함께 export 시점의 remote URL 과 HEAD SHA 를 적은
manifest 가 들어갑니다.

**import 는 덮어쓰지 않고 묻지도 않습니다.** 없던 파일은 추가하고, 바이트가
같은 파일은 그대로 둡니다. 그래서 같은 zip 을 다시 받아도 아무것도 쓰지
않습니다. 바이트가 다르면 받은 쪽을 옆에 놓습니다. `ledger/<id>.md` 옆의
`ledger/<id>.incoming.md` 입니다. 그리고 그 목록을 알려 줍니다. 둘 중
어느 쪽이 맞는지는 합치는 일이 아니라 읽는 일이고, 명령이 어느 쪽을 골라도
어떤 경우에는 작업을 버리게 됩니다. 그다음 `evidence-check .` 이 이 트리에
대해 어느 행이 어긋났는지 알려 줍니다.

다음 경우에는 아무것도 쓰지 않고 멈춥니다. zip 이 다른 저장소에서 나온
경우(같은 저장소를 두 가지로 적은 것이라면 `--allow-other-repo`), manifest 가
이 빌드는 읽지 못하는 형식을 적어 놓은 경우, 멤버가
루트 밖으로 나가는 경우, 멤버 하나 또는 zip 전체가 기록의 루트가 담을 수
있는 것보다 큰 크기나 많은 개수를 적어 놓은 경우, 멤버를 읽을 수 없는
경우(체크섬이 안 맞거나, 암호화돼 있거나, 이 빌드에 해제기가 없는 압축
방식인 경우), 디렉터리여야 하는 이름이 zip 안에서든 루트에서든 파일인 경우, 두
루트가 이미 다 있는 경우입니다.

여기까지는 모두 첫 바이트를 쓰기 전에 멈춥니다. 하나는 그럴 수 없습니다.
루트 안에 쓸 수 없는 디렉터리가 있거나 디스크가 가득 차면 복사가 도중에
멈추고, 파일시스템이 뭐라고 했는지 알려 줍니다. 그것을 고치고 다시 실행하면
됩니다. 아무것도 덮어쓰지 않으므로 두 번째 실행이 남은 복사를 끝내고, 이미
있던 것은 바이트가 같다고 알려 줍니다.

충돌한 파일이 비켜 갈 이름이 심볼릭 링크면 그 이름은 이미 찬 것으로 봅니다.
사본은 그다음 빈 이름에 놓이고, 링크를 뚫고 쓰지 않습니다. `seal export` 도
zip 이름을 같은 방식으로 다룹니다. 쓰는 도중에 쓰는 임시 이름 자리에 이미
무언가 있으면 거부하고 그대로 둡니다. 쓰다 만 압축 파일은 자기가 치우지만,
거기 있던 것은 건드리지 않습니다.
`seal import --into shared` 나 `--into local` 은 지정한 모드의 루트를
만들어 줍니다. 모드를 바꾸는 다른 방법이기도 합니다. export 하고, 다른
자리로 import 하고, 커밋하거나 지웁니다.

shared 모드에서 `seal export` 는 zip 을 쓰지 않습니다. 기록이 이미
커밋돼 있어서 모든 클론과 CI 가 갖고 있기 때문입니다. 대신 그 경로와
local 로 바꾸는 `mv` 명령을 알려 줍니다. 릴리스마다 한 번,
`seal export --check` 가 지난 export 이후 몇 개의 작업 항목이 바뀌었는지
한 줄로 알려 주고, 어디에도 올리지 않습니다. 복사본을 어디에 두는지는
쓰는 사람의 일입니다.

## 한계

무엇을 하지 않는지가 무엇을 하는지만큼 중요합니다.

- **게이트는 판단을 넘길 뿐, 막지 않습니다.** 커밋 게이트는 커밋을 세우고 갈 수 있는
  길을 선택지로 내밀며, 다시 시도하면 승인이 곧 면제인 일반 확인창이 뜹니다. 명령에
  `[no-review]` 를 넣으면 아예 건너뜁니다. 리뷰 없이 커밋하려는 에이전트에게
  과속방지턱이지 보안 장치가 아닙니다. 확인창에 답할 수 있는 사람이면 누구나 커밋할
  수 있습니다.
- **evidence-check 는 인용이 아직 유효한지만 증명합니다.** 그 인용이 뒷받침하는 주장이
  여전히 맞다는 뜻은 아닙니다. `DRIFTED` 는 다시 확인해야 한다는 표시이지 틀렸다는
  판정이 아니고, 좌표는 그대로인데 코드의 의미만 바뀐 경우는 `OK` 로 나옵니다.
- **증명 블록은 강제가 아니라 공개입니다.** 어떤 훅도 그 내용을 검사하지 않습니다.
  `none — <이유>` 로 채워진 줄이 사용자 눈에 그대로 보인다는 것이 이 장치의
  값어치입니다.
- **"광역은 한 번" 은 에이전트가 따르는 규칙이지 게이트가 아닙니다.** 회차 도중에 전
  스위트를 도는 것을 막는 장치는 없습니다. 있는 것은 지시문과 warden 의 봉인 감사,
  그리고 되풀이를 눈에 띄게 만드는 `round-N.md` 의 필드뿐입니다. 애초에 훅으로는
  구분할 수 없습니다 — 회차가 끝났는지는 실행되는 명령의 속성이 아니니까요.
- **`Fixes checked by: nobody` 는 한 자리에서만 막습니다.** 마지막 회차 기록에서
  `Pass` 가 체크된 채로 이 값이 적혀 있으면 PR 이 깨집니다. 자기 지적을 닫은
  수정을 아무도 안 읽었는데 리뷰가 통과했다고 말할 수는 없어서입니다. 그 밖의
  자리에서는 출력만 합니다. 이 규칙이 들어오기 전에 시작된 작업 항목은 아예
  제외됩니다. 아무도 되돌릴 수 없는 머지된 이력에서 처음부터 빨간불이 켜지는
  검사는, 사람들이 건너뛰는 법을 먼저 배우는 검사입니다. 빠져나가는 길은 회차를
  쓰지 않습니다 — 그 수정의 diff 를 대상으로 검증 회차를 한 번 띄우면 됩니다.
- **원본 대조 표시는 대조했다는 뜻이지 잘 대조했다는 뜻이 아닙니다.** 게이트는 이번
  HEAD 에 대해 대조 기록이 있는지만 봅니다. 대조의 질은 리뷰어의 몫이고, 하지도 않은
  대조에 표시를 남기면 "아무도 확인 안 함" 이 "확인했고 괜찮았음" 으로 뒤바뀝니다.
- **세션 탐지는 추론입니다.** 확장에서 실행되는 세션은 프로세스 이름이 `claude` 가
  아니고, 다른 디렉터리에서 이 트리를 고치는 세션은 여기에 흔적을 남기지 않습니다.
  lease 가 그 틈을 대부분 메우지만 최근에 도구를 호출한 세션에 한합니다. 탐지가
  불가능한 환경에서는 가드가 스스로 판정하지 않고 갈 수 있는 두 길을 내밀며, 그
  다음 시도는 일반 확인창이라 어떤 환경도 막혀 버리지 않습니다.
- **Windows 는 실제 기계에서 한 번 돌았고, 거기 결함이 하나 남아 있습니다.**
  2026-08-26 까지 이 자리는 `windows-latest` 스위트가 통과한다고 적고 있었지만
  통과하지 않았습니다 — 72 개가 실패했고, 이슈로 기록된 뒤 네이티브
  Windows 11 트리에서 고쳤습니다. 진입점도 같은 기계에서 측정했습니다.
  `hooks/hooks.json` 의 명령줄을 `cmd.exe` 로, 옵트인한 저장소를 향해 실행하면
  `deny` 가 한 번 나오고 그다음 `ask` 가 나옵니다. `python3` 이 PATH 에서
  잡혔으므로 `py -3` 폴백은 Windows 에서 여전히 실행된 적이 없습니다 — 그쪽은
  POSIX 에서 첫 이름을 PATH 에서 없애고 확인한 것입니다. 그 옆에 있던 콘솔
  인코딩 결함은 닫혔습니다. 한국어 cp949 콘솔에서 `PYTHONUTF8=1` 없이
  맨 `pytest tests/` 가 전부 통과합니다.
- **적합성 eval 은 한 번도 실행되지 않았습니다.** `evals/` 는 early access 기능인
  `claude plugin eval` 을 대상으로 작성했고 활성화를 기다리는 중입니다. 러너 없이 확인할
  수 있는 것 — 필수 필드와 케이스별 grader 존재 — 은 CI 가 봅니다. 통과한 것이 아니라
  작성만 된 상태로 보시면 됩니다.

## 기여

게이트를 고치는 변경은 나머지보다 기준이 높습니다. 게이트가 남의 커밋을 통과시킬지
말지를 정하기 때문입니다. 고치기 전에 실패하는 것을 직접 본 테스트, 이 변경이 막는
쪽으로 기우는지 뚫는 쪽으로 기우는지에 대한 진술, 그리고 검증하지 못한 플랫폼에 대한
정직함을 요구합니다. [CONTRIBUTING.md](./CONTRIBUTING.md) 를 보세요.

## 언어 정책

기능 파일(스킬·에이전트·훅·커맨드)은 영어 하나로만 씁니다. 모델 컨텍스트에
로드되는 파일이라, 번역본을 따로 두면 반드시 원본과 어긋나기 때문입니다.
한국어는 사람이 읽는 문서에만 둡니다. 일부러 둔 예외가 하나 있습니다.
writing-style 스킬은 한국어 항목과 영어 항목을 따로 담는데, 이는 서로를 옮긴
번역본이 아니라 각 언어의 독립된 규범이라 앞의 어긋남 문제가 해당되지
않습니다. 응답 언어는 사용자 자신의 CLAUDE.md 설정을 따르며, 배포되는 블록은
언어를 강제하지 않습니다.
