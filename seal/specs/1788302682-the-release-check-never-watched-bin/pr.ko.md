# 릴리스 검사가 `bin/` 을 한 번도 보지 않았고, 무엇을 보는지 고정한 것도 없었습니다

<!-- PR #<번호> 본문의 한국어판. 영어 본문이 정본이고 이 파일이 번역입니다. -->

`main` 으로 들어오는 PR 이 배포되는 것을 바꾸면 hygiene 워크플로가 버전을
올렸는지 확인합니다. 그 검사는 다섯 루트만 봤습니다. `skills/`, `agents/`,
`hooks/`, `templates/`, `.claude-plugin/` 입니다. `bin/` 은 없었습니다.
`bin/` 에는 사용자가 실제로 치는 명령 네 개가 들어 있고, 플러그인이 켜져 있는
동안 Claude Code 가 그 폴더를 Bash 툴의 PATH 에 올립니다. 그러니 래퍼 하나만
고친 PR 은 버전을 움직이지 않은 채 사용자에게 나갔을 것이고, 업데이트는
버전으로만 알려지므로 아무도 그 변경을 받지 못했을 것입니다.

## 무엇이 달라지나

| | 이전 | 이후 |
|---|---|---|
| `bin/` 만 바꾼 PR 이 `main` 으로 들어올 때 | 검사가 침묵하고, 버전이 그대로면 아무도 업데이트를 받지 못합니다 | 다른 다섯 루트와 같이 버전 이동을 요구합니다 |
| 패턴에서 루트 하나가 빠지거나 하나가 늘어날 때 | 알아채는 것이 없습니다. `bin/` 이 빠진 것도 검사가 아니라 다른 변경을 쓰다가 눈에 띄었습니다 | 테스트가 워크플로에서 패턴을 읽어 와 여섯 루트 집합과 같은지 확인합니다 |
| 최상위에 새 폴더가 생길 때 (`commands/` 같은 것) | 배포되는지 아닌지 아무도 정하지 않은 채 남습니다 | 그 폴더를 "배포됨" 이나 "저장소 내부" 중 하나로 분류할 때까지 스위트가 실패합니다 |
| `docs/branch-and-release.md` 가 이름하는 루트 | 다섯 | 워크플로와 같은 여섯. 문서와 패턴이 어긋나면 테스트가 실패합니다 |

## 다섯 루트 밖에 사용자가 직접 실행하는 것이 또 있는가

이슈의 둘째 항목입니다. 최상위 항목을 전부 열어 보고 답했습니다.

- **`bin/` 은 배포됩니다.** 이 세션의 PATH 에서 `evidence-check` 가 플러그인
  캐시의 `bin/` 으로 해석되는 것을 실행으로 확인했고, 플러그인 레퍼런스의
  *File locations* 도 같은 말을 합니다.
- **`install.sh` · `uninstall.sh` 는 제외합니다.** 클론에서 `bash install.sh`
  로 직접 실행하는 파일이고, 플러그인 로더가 읽지 않습니다. 클론은 버전과
  무관하게 항상 최신입니다.
- **`docs/` 는 제외합니다.** 배포되는 파일이 `docs/` 를 인용하지만 런타임에
  여는 곳은 없고, 인용 경로는 사용자 저장소의 `docs/` 로 해석됩니다.
- 나머지 (`tests/`, `specs/`, `evals/`, `.github/`, 최상위 문서들) 는 이
  저장소 자체의 작업물이라 플러그인을 통해 사용자에게 닿지 않습니다.

## 리뷰 체인

두 라운드를 돌았고 기록은 작업 항목 폴더에 있습니다. 라운드 1 은 차단 발견
없이 🟡 두 건을 열었습니다. 문서 쪽 테스트가 여섯 루트가 *있는지* 만 보고
일곱째가 들어와도 통과하던 것, 그리고 스텝 이름이 바뀌면 메시지 없는
`IndexError` 로 실패하던 것입니다. 수정 패스는 같은 smith 세션을 이어서
돌렸고, 라운드 2 가 그 diff 만 대상으로 두 건 모두 닫혔음을 변이로 확인했습니다.

## 호환성

워크플로 한 줄과 문서 한 문장, 테스트 파일 하나입니다. 플러그인 사용자에게
달라지는 것은 없습니다.
