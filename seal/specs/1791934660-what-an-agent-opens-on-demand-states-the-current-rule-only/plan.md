## Summary

One branch, nine phases, one file or one coupled group per phase, each on #923's check and harness. Phase 1 proves the batch shape on the file in every prefix, `CLAUDE.md` with its block template: the smallest rewrite, the full ledger, pin, sync and eval procedure, and the record test widened so an on-demand file owes a record. Phase 2 takes the largest file. Phase 3 builds the orchestrator cases and their baseline, because phases 4 and 5 rewrite the orchestrating session's own instructions and nothing in #923's suite reads as that session. The rest follow in order of opens × bytes, with files that share a test module or a `BASELINE` pair in one phase. Every row only lowers; nothing asks a person; CI gains one test's scope and no job.

**What breaks in 6 months with the chosen approach.** The orchestrator cases drift from the real orchestrator: the installed plugin is the cache, so the rewritten `orchestration.md` meets its first real session only after 0.22.0 ships, and a rule the five cases do not reach surfaces as a run that forgot it — the `check:` rows are what catches those, and the census's `not exercisable` list is read by the round. A template's one-line cell comment loses the nuance its paragraph carried and a record is filled wrong: the checkers that parse the record (`round_record.py`, `chain_check.py`, `hooks/routing.py`) refuse the wrong vocabulary, and the link in the comment is where the writer reads the rest. The `bytes:` rows hold the files at their compact size while a story is written back in place of a rule: the suite catches it where an output shows the rule, review's stage 1 against the shape catches the rest, and `history:` catches a story that carries a mark. A file's readers change — an agent starts opening a skill no spawn opened at this frame — and its phase ran the wrong suites: the opens census is dated and in `spec.md`, and the next frame re-takes it.
