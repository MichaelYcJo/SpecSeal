## What this phase found

**M1's number is six, not one, and it depends on an axis the frame did not
name.** Thirteen steps, of which three were mirrored before this work
(`unverified`, `chain`, `survivors`). Of the ten that were not, six have a
local answer and four have none:

| No local answer | Why |
|---|---|
| every issue this pull request claims | the pull request's body |
| the pull request heads a round record may name | a fetch of the remote's pull-request namespace |
| the milestone this release claims | the tracker, through `gh` |
| both READMEs move together | it warns and never fails, so there is no verdict to mirror |

The six with a local answer split again, on a line the frame did not draw and
the build had to: **whether the check is something the plugin ships.**

| Local answer | Ships with the plugin | Verdict |
|---|---|---|
| no merge dropped a correction | `skills/evidence-check/scripts/correction_check.py` | an arm, phase 2 |
| the mode the row declares | `skills/implement/scripts/seal.py` | an arm, phase 2 |
| every changelog fragment reached the released file | `.github/scripts/gather_changelog.py` | excluded |
| every ledger fragment folded | `.github/scripts/fold_ledger.py` | excluded |
| the CLAUDE.md block is the template's | `.github/scripts/claude_block.py` | excluded |
| a change to what ships must move the version | inline shell, no script at all | excluded |

`broad_gate.py` ships to every repository that installs the plugin, so an arm
that runs `.github/scripts/…` would be an arm that exists in one repository
and fails in the rest. `seal/config.md`'s `Broad gate` row is the place a
repository names a check of its own, and that is where those four belong —
which is a decision for the owner rather than for this build, so it is a row
in `questions.md` rather than a commit.

So: **six could be mirrored and were not; two of the six are mirrored by the
end of phase 2, and four stay excluded with that reason written out.** The
frame's warning was right — "it is one" would have been wrong by five.

**The reader was partial and being driven is what said so.** The first
spelling split the text on `"\njobs:\n"`, which cannot see a `jobs:` on the
first line of a file. The fragment cases found it before the workflow could.

**One unit was written, mutated, and deleted.** `job_steps` dropped comment
lines before matching. Removing that line left the module green at 10 passed:
both patterns already require the first non-blank character to be the list's
dash or a job key's letter, so a commented-out step can never match either.
The case that pins it stays — it goes red when `STEP_RE` stops anchoring on
the dash, measured — and the dead branch went.

**A1 and A2 are red on different edits, which is what `spec.md` asks for.**
Adding a fourteenth step to the workflow reddens A1 alone; deleting a step
whose row stands reddens A2 alone with A1 green; renaming one reddens both.

**The partition names two arms that do not exist until phase 2.** That is the
plan's shape rather than an oversight: A3 — a named arm actually runs — is
phase 2's row, and it is written in phase 2 against the arms that phase adds.
