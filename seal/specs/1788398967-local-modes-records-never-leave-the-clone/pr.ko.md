# local 모드의 기록이 클론을 못 떠났고, 이제 사본이 오갈 수 있습니다

## 무엇이 달라지는가

local 모드는 대조표와 작업 항목 기록을 git 디렉터리 아래 둡니다. 그래서 트리에
안 들어가고 커밋도 안 됩니다. 그게 이 모드의 목적인데, 동시에 새 기계나 다시
받은 클론은 아무것도 없이 시작한다는 뜻입니다. 사본을 들고 갈 방법이 없으면
local 모드는 *두고 간다* 가 아니라 *잃는다* 로 읽힙니다.

명령 둘이 그 답입니다.

`seal export` 는 루트만, 오직 루트만 `seal-<저장소>-<날짜>.zip` 으로 묶어
**클론 옆에** 놓습니다. 안이 아니라 옆입니다. 작업 트리 안의 추적 안 되는 zip
은 `git add -A` 한 번이면 커밋되고, 그건 local 모드가 트리 밖에 두려던 바로 그
기록입니다. zip 에는 저장소의 remote, 그때의 커밋, 작업 항목별 요약값을 적은
명세가 함께 들어갑니다.

`seal import` 는 아무것도 덮어쓰지 않고 묻지도 않습니다. 파일마다 새로 놓거나,
바이트가 같으면 그대로 두거나, 다르면 `<이름>.incoming<확장자>` 로 옆에 놓고
알려 줍니다. 충돌한 둘 중 어느 쪽이 맞는지는 합치는 일이 아니라 읽는 일이고,
명령이 어느 쪽을 골라도 어떤 경우에는 작업을 버리게 됩니다.

모드를 바꾸는 길이기도 합니다. `seal import --into shared` 나 `--into local` 이
지정한 모드의 루트를 만들어 주므로, 전환은 export 하고 다른 자리로 import 하고
커밋하거나 지우는 것입니다.

local 모드에서는 릴리스 때 기록이 다른 어딘가에도 있다고 말해 주는 것이
없습니다. `seal export --check` 이 한 줄을 찍습니다 — 지난 export 이후 몇 개의
작업 항목이 바뀌었는지. 어디에도 올리지 않습니다. 사본을 어디 둘지는 쓰는 사람
몫입니다.

## 세션 상태는 아무 일도 하지 않습니다

smith 표식, 워크트리 선택, 리뷰·대조 표식, 일회용 opt-out, 리스 파일은 루트
**옆에** 있지 안에 있지 않습니다. export 는 루트만 걷기 때문에, 이것들이 빠지는
것은 누가 관리하는 목록이 아니라 구조 자체입니다. 그 구조에서 빠져나가는 유일한
길이 루트 안의 심볼릭 링크라, 링크는 따라가지 않고 건너뛰며 이름을 알려 줍니다.

## zip 은 남의 기계가 만든 파일이고, 그 뜻을 말하는 데 다섯 라운드가 걸렸습니다

이 작업은 문장 하나를 전제로 계획됐습니다 — *`extractall` 은 경로 탈출의
고전적인 자리다.* 이 플러그인이 도는 파이썬에서 그건 **거짓**입니다. `..` 과 앞의
`/` 를 이미 걸러내고, 링크 항목은 평범한 파일로 씁니다. 파이썬 세 종류에서
직접 재 봤습니다. 진짜로 실격 사유인 것은 덮어쓴다는 것, 그리고 받는 쪽에 이미
있는 심볼릭 링크를 따라간다는 것입니다.

그 두 번째가 사례 하나가 아니라 **부류**였고, 리뷰 사슬이 서로 다른 자리에서 세
번 찾았습니다. 매번 직전 수정이 멈춘 데서 이름 하나 옆이었습니다.

1. **기록 자신의 이름** — 거기 끊어진 링크가 있으면 파일이 없는 것으로 읽혀 새
   파일 취급을 받고, 링크를 따라 루트 밖에 그대로 쓰입니다. exit 0, 출력 한 줄
   없이.
2. **충돌이 비켜 가는 이름** — 첫 번째를 막은 검사가 `<이름>.incoming<확장자>`
   를 한 번도 본 적이 없었습니다. 게다가 충돌을 일으킬지 말지는 zip 을 보내는
   쪽이 다른 바이트를 보내기만 하면 됩니다.
3. **export 가 쓰는 이름** — `seal-<저장소>-<날짜>.zip.partial` 은 클론 옆에
   있고 완전히 예측 가능합니다. 거기 링크를 걸면 명세와 기록 전부가 밖으로
   나갔습니다.

셋 다 두 겹으로 막았습니다. 후보 이름을 전부 파일이 아니라 링크로 읽고, 쓰기는
링크를 뚫거나 있는 파일을 덮는 것을 커널이 거부하는 방식으로 엽니다.

다섯 라운드가 산 다른 하나는 **어떤 zip 도 이 명령을 파이썬 traceback 으로
끝내지 못한다**는 것입니다. 예전에는 일곱 갈래로 그랬습니다 — 이 빌드가 풀 수
없는 압축 방식, 암호화된 멤버, 기록과 명세 각각의 체크섬 불일치, zip 에는
디렉터리여야 하는데 루트에는 파일인 이름, 복사가 들어갈 수 없는 디렉터리, 그리고
명세의 필드가 엉뚱한 자료형인 경우. 마지막이 가장 나빴습니다. 복사는 이미
성공했는데 사람은 exit 1 과 traceback 을 봤고, exit 1 은 *아무 일도 없었다* 로
읽힙니다.

## 이제 남의 기계에 건네도 되는 것

zip 은 신뢰할 수 없는 입력이고, 한 바이트도 쓰기 전에 거부하는 것은 이렇습니다.

- 다른 저장소에서 나온 zip (같은 저장소를 두 가지로 적은 것이면
  `--allow-other-repo`)
- 이 빌드가 읽지 못하는 형식을 적은 명세
- 이름으로든 링크를 통해서든 루트 밖에 떨어질 멤버
- 기록의 루트가 담을 수 있는 것보다 큰 크기나 많은 개수를 적은 멤버 또는 zip —
  32 MB, 512 MB, 2만 개이고 셋 다 첫 쓰기 전에 읽습니다. 408 KB 짜리 zip 이
  400 MB 를 적어 두고 419 MB 를 0.2 초에 쓴 것을 재고 정한 값입니다
- 데이터가 아예 읽히지 않는 멤버
- zip 에는 디렉터리여야 하는데 파일인 이름 — 어느 쪽에 있든
- 두 모드의 루트를 이미 다 갖고 있는 클론

첫 바이트 전에 못 멈추는 것이 하나 있습니다. 루트 안에 쓸 수 없는 디렉터리가
있거나 디스크가 가득 찬 경우입니다. 그건 도중에 멈추고, 파일 시스템이 뭐라고
했는지 알려 주고, 되살릴 수 있게 만드는 사실을 말합니다 — 아무것도 덮어쓰지
않으므로 다시 실행하면 남은 복사가 끝납니다.

## 운영에 영향을 주는 것

- **새 명령 한 쌍** — `bin/seal` 과 Windows 짝, 그리고 그 뒤의
  `skills/implement/scripts/seal.py`. 그 밖에 모양이 바뀐 것은 없습니다.
- **`hooks/optin.py` 에 도우미 하나** — `home_paths` 입니다. `home_at` 은 지금
  있는 모드밖에 못 알려 주는데 `--into` 는 지금 없는 쪽을 가리켜야 합니다. 기존
  호출처 일곱 곳을 전부 읽어 아무 영향이 없음을 확인했습니다.
- **상태 파일 하나** — `<git-common-dir>/specseal-last-export.json` 이고 루트
  안이 아니라 옆입니다. 세션 상태라 zip 에 절대 안 들어갑니다.

| 무엇 | 결과 |

| 전체 스위트, 머지 커밋에서 | 1519 통과, 1 skip |
| `ruff check .` · `ruff format --check .` | 깨끗 · 83 파일 |
| 근거 대조표, strict | 408 행 정상 · 어긋남 0 · 깨짐 0 |

| 수정마다 추가한 단위 전부 | 하나씩 되돌려 봄. 각각 자기 케이스만 빨개짐 |
| 세 개의 탈출구 | 각각 수정 전후로 재현. exit 0 에 기록이 루트 밖, 그다음 거부에 아무것도 안 씀 |

변이 검사는 한 문장 따로 적을 값을 했습니다. 읽어서는 못 잡을 것을 잡았습니다 —
형식 거부를 붙잡으려고 심은 케이스가 `format-2.zip` 이라는 픽스처에 대고
`"format" in out` 을 단언하고 있었는데, 메시지가 경로를 찍습니다. 결함일 때도
참이고 고친 뒤에도 참이었습니다. 수정을 되돌려 봐서 나왔습니다.

## 소유자 판단으로 남긴 것

- **릴리스 알림이 N=1 일 때 `1 work items changed` 로 나옵니다.** 설계 문서와
  이슈가 그 문장을 그대로 적고 있어서 인용문으로 보고 손대지 않았습니다.
  바꾸시겠다면 한 단어입니다.
- **루트 자체가 심볼릭 링크면** 따라가서 가리키는 곳에 전부 씁니다. 루트를 일부러
  다른 자리에 둔 사람이 원하는 동작이기도 해서, 결함이 아니라 질문으로 남깁니다.
- **32 MB, 512 MB, 2만 개가 맞는 숫자인지.** 아직 어떤 기록도 근처에 못 갔습니다.
- **`questions.md` 의 질문 셋** — 각각 거기 적힌 기본값으로 만들었습니다.

라운드에서 나온 둘은 여기가 아니라 이슈로 갔습니다. export 의 크기는 아무도 접지
않은 작업 항목이 정하는데 zip 이 들고 가기 어려워질 때까지 아무 말이 없다는 것
(#101), 그리고 근거 검사기가 16진수가 아닌 해시를 가진 행을 세지도 이름을 부르지도
않고 버린다는 것(#97)입니다.
