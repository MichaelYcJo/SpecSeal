| Q1 | The gate refuses on `M \ D`: the milestone claims an open issue the release branch does not carry. Separately it finds `L ≠ D` — a label that disagrees with the commits. Does that disagreement **fail** the release pull request, or report and pass? | a person | **(a) fail.** A label written by hand, or a signal run that did not happen, stops the release until somebody repairs the labels — a red build for something that does not change what ships. **(b) report and pass.** The labels can rot silently, and the human-readable signal quietly stops being true, which is the defect one layer over. **(c) fail one direction only** — `L \ D` (a label naming a release the issue is not in) fails, `D \ L` (the signal missed one) reports. The repository's own precedent is split: `issue_claims_check.py` reports and never fails because "a check that goes red on prose stops a release for a false positive"; `survivor_check.py` fails | **(c)**. `L \ D` is always somebody's hand-edit and is always one command from fixed; `D \ L` is the signal failing, and blocking a release on it makes the release pay for the signal's outage | ✅ **(c)** — 2026-09-11, the repository owner, taken as the default the frame proposed. `L \ D` (a label on an issue this release does not carry) FAILS: it is always a hand-edit or a squash subject that lost its `(#N)`, and one command repairs it. `D \ L` (the signal missed one) REPORTS: a release must not be held for a failure of the signal rather than of its contents.
