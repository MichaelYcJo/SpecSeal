# 게이트를 바꿀 때 세 가지를 묻는데, 사람을 몇 번 세우는지는 안 묻습니다

<!-- PR #<번호> 본문의 한국어판. 영어 본문이 정본이고 이 파일이 번역입니다. -->

`CONTRIBUTING.md` 는 게이트를 바꾸는 변경에 세 가지를 요구합니다. 빨간 것을
직접 본 테스트, 어느 방향으로 틀릴지 밝히기, 플랫폼 정직성입니다. **그 변경이
키보드 앞의 사람에게 무엇을 물리는지는 묻지 않습니다.**

## 무엇이 달라지나

네 번째 항목이 생깁니다. **프롬프트 예산**이고, PR 본문에서 답합니다.

- 이 변경은 세션당 몇 번 사람을 세우는가
- 하나라도 늘린다면, 더 싼 방법이 왜 같은 보장에 못 닿는가. 파일에서 읽는 값,
  글로 적어 두는 기본값, 에이전트가 스스로 하는 거절 같은 것들입니다

그리고 그 예산이 무엇을 위해 쓰이는지를, **절차를 따르는 자리가 아니라 설계를
고르는 자리에** 적었습니다. 무인으로 도는 검증이 이 프로젝트의 제1 목표라는
문장입니다.

| | 이전 | 이후 |
|---|---|---|
| 거부하는 검사와 출력만 하는 검사 중 고를 때 | 프롬프트가 비용이라고 말해 주는 것이 없습니다. 누가 기억할 때만 싼 쪽이 이깁니다 | PR 본문에서 근거를 대야 합니다 |
| 세션당 질문을 하나 늘리는 게이트 PR | 세 항목만 답하면 통과합니다 | 네 번째를 답해야 하고, 그것은 어떤 테스트도 대신 답해 줄 수 없는 항목입니다 |
| 플러그인을 설치한 사람 | — | 달라지는 것이 없습니다. 두 파일 모두 기여자용입니다 |

## 규칙이 없던 게 아니라 읽는 사람이 없었습니다

규칙은 이미 쓰여 있고 이미 배포됩니다. `skills/implement/SKILL.md` 1절이
*"질문의 비용은 난이도가 아니라 도착 시점이다"* 와 *"yes/no 가 곧 신호다"* 를
적어 두었습니다. `docs/review-chain-spec.md` 는 같은 논리를 훅 층위에 적용한
것이고, 리뷰 스킬 게이트가 `ask` 대신 `deny` 를 쓰는 이유이자 두 팔이 한
호출로 묶이는 이유입니다.

빠진 것은 읽는 사람입니다. `implement` 는 절차를 따르는 에이전트가 불러오는
문서입니다. 두 메커니즘 중 하나를 고르는 사람은 티켓과 `CONTRIBUTING.md` 를
읽습니다.

## 건드리지 않은 것

배포되는 `CLAUDE.md` 블록은 크기를 그대로 둡니다. README 의 *"항상 켜진
컨텍스트가 왜 12줄인가"* 는 측정치를 근거로 내린 결정이고, `implement` 가 이미
그 규칙을 모든 세션에 나릅니다. 새로 쓴 목표 문장은 저장소 로컬 절반에 있으며,
`install.sh` 는 그쪽을 배포하지 않습니다.
