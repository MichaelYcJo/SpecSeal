# writing-style — 리뷰 코멘트가 아닌 글

`skills/writing-style/SKILL.md` 이 담고 있던 세 절이다. 읽는 사람이 코드 리뷰
밖에 있는 글 — PR 본문, 다른 팀에 답하는 코멘트, 터미널에서 사용자에게 하는
답 — 을 쓸 때 여는 파일이고, 「리뷰 코멘트에만 해당하는 것」은 저 파일에 남아
있다.

**여기 있는 것은 문장 규칙이 아니다.** 「먼저 — 무엇을 쓰는 글인가」·「문장
규칙」·「구성 규칙」·「English prose rules」·「스스로 점검하는 법」은 모두
`skills/writing-style/SKILL.md` 에 있고, 아래 세 절은 그 **위에 더해지는**
것이지 대신하는 것이 아니다. 이 파일만 열고 표만 적용한 PR 본문이 실제로
나갔고, 읽는 사람이 너무 어렵다고 돌려보냈다 — 그래서 각 절 머리에 그 사실이
다시 적혀 있다.

리뷰어는 이 파일을 열지 않는다. `warden` 이 쓰는 글은 리뷰 코멘트와 리포트뿐인데
이 세 절이 스폰마다 함께 도착하고 있었다 (#265).

## PR 본문에만 해당하는 것

**여기에 오기 전에**: 출력 언어의 문장 규칙이 먼저 적용된다 — 한국어면
「문장 규칙」, 영어면 「English prose rules」. 아래 표는 그 위에 **더해지는**
것이지 대신하는 것이 아니다. 이 줄이 없어서 실제로 아래 표만 적용한 PR 본문이
나갔고, 읽는 사람이 너무 어렵다고 돌려보냈다.

### 도메인 용어를 쉬운 말로 바꾼다

**리뷰 코멘트는 그 코드를 아는 사람이 읽고, PR 본문은 그렇지 않은 사람도 읽는다.** 기획·QA·다른 팀·6개월 뒤의 자신이다.

| 나쁨 (도메인 용어) | 좋음 (쉬운 말) |
|---|---|
| 리뷰 존재 여부로 판정합니다 | 후기가 있는지로 판단합니다 |
| 조회 조건에 리뷰 선행이 들어 있습니다 | 후기를 쓴 주문만 목록에 나옵니다 |
| 같은 술어를 한 벌로 묶었습니다 | 같은 판단을 하는 코드를 한 군데로 모았습니다 |
| 복제 지연 동안 read-your-writes 가 깨집니다 | 방금 쓴 내용이 아직 복사 안 된 DB 를 읽어서 못 찾습니다 |

**남겨도 되는 것**: 필드명·엔드포인트·에러 코드처럼 **클라이언트가 실제로 쓰는 이름**. 이건 정확해야 하므로 그대로 쓴다.

### 왜 그렇게 했는지를 한 문장으로 잇는다

*"A 로 했습니다"* 만 쓰면 읽는 사람이 판단할 수 없다. **그렇게 안 하면 무슨 일이 생기는지**를 한 문장 붙인다. 셋 이상이 얽힌 것은 **번호로 나열**한다.

### 파일 단위 나열을 하지 않는다

| 나쁨 | 좋음 |
|---|---|
| `auth_service.py` 에 `login_with_email` 함수 추가 | 이메일 + 비밀번호 로그인 흐름을 도입했습니다 |
| `user.py` 의 `password_hash` 컬럼 타입 변경 | 비밀번호 해싱을 bcrypt 에서 argon2id 로 바꿨습니다 (기존 사용자는 다음 로그인 때 자동 이전) |

### 운영에 영향을 주는 것은 따로 뺀다

마이그레이션 · 새 환경 변수 · 새 의존성 · 호환성 깨짐은 **본문에 섞지 말고 별도 항목**으로 적는다.

### 검증한 것을 표로 남긴다

무엇을 어떻게 확인했는지 적는다. **테스트가 실제로 결함을 잡는지 확인했다면 그것도 적는다** — 통과 숫자만으로는 그 테스트가 아무것도 검증하지 않아도 알 수 없다.

## 다른 팀에 답할 때

기획·프론트가 남긴 확인 요청에 답하는 글이다. 상대는 내 코드도 내 문서도 열지 않고, 내 답을 근거로 **자기 쪽 구현을 정한다.**

> **이 절의 규칙이 앞의 문장 규칙을 덮는다.** 「확신의 정도」는 확인한 것을 단정하라고 하지만, 여기서는 **내가 확인한 것에도 관측 종결어미를 쓴다** — 어조가 곧 협업 태도로 읽히기 때문이다.

- **머리에 수신자와 정정 요청 한 줄을 둔다.** 멘션 + `cc)`, 그리고 *"다르게 인지하거나 수정사항이 있다면 노티 부탁드립니다"* 한 줄이면 항목마다 "이견 있으시면"을 반복하지 않아도 된다.
- **근거 출처를 문장 앞에 밝히고, 내 결론에도 `확인됩니다` · `파악됩니다`.** 직접 열어 본 사실이어도 단정형은 협의가 아니라 통보로 읽힌다. 지금 시점의 사실은 `현재` 를 앞에 둔다.
- **상대의 판정 근거를 되묻지 않는다.** 사실을 주면 상대가 자기 규칙을 스스로 맞춘다. 확인 요청은 **우리가 정한 것**(파라미터 형태·응답 규약)에 대해서만 한다.
- **상대 선택지를 깎는 논증을 넣지 않는다.** 우리 근거와 결론만 적으면 충분하다.
- **각 항목을 우리 쪽 행동으로 닫는다.** `~하겠습니다` · `~할 예정입니다` · `~해야 할 것 같습니다`(완곡한 제안 — 상대 화면 설계를 바꾸는 결정일수록 이 형태).
- **상대가 쓰는 말로 적고, 내부 메커니즘은 괄호로 내린다.**
- **정책 조항 번호·내부 문서를 참조하지 않는다.** 상대가 열 수 없는 자리다. 내용 자체를 풀어서 적는다.
- **항목이 셋 이상이면 글머리 기호로 끊는다.** 상대는 자기 화면에 옮길 것만 골라 읽는다.

```
나쁨   거부되는 것은 둘 다 켜서 보내는 경우입니다. 접수를 마쳐야 추가 요청이 열리므로
       두 조건을 모두 만족하는 건이 존재할 수 없어서입니다.
좋음   서버 코드에서 확인해본 결과 거부되는 것은 둘 다 켜서 보내는 경우로 파악됩니다.
       접수를 마쳐야 추가 요청이 열리므로 두 조건을 모두 만족하는 건이
       존재할 수 없어서로 확인됩니다. (현재 로직 그대로 유지할 예정입니다.)
```

## 사용자와의 대화에만 해당하는 것

터미널에서 사용자에게 답하는 글이다. **이 표에서 가장 자주 쓰는 글인데 문체는
가장 다르다.** PR 본문을 쓰다가 그대로 대화로 넘어오면 읽히지 않는다.

**앞의 문장 규칙은 그대로 적용된다.** 아래는 그 위에 더해진다.

- **결론 먼저, 짧은 문장.** 사용자는 다음에 무엇을 할지 정하려고 읽는다.
  근거는 결론 뒤에 한 줄이면 된다.
- **이 저장소가 만든 말을 쓰지 않는다.** 「은어와 압축 한자어를 풀어쓴다」의
  판별법이 여기서 가장 세게 걸린다. 대화 상대는 방금 그 코드를 같이 본
  사람이라 은어가 통할 것 같지만, 통하는 것과 빨리 읽히는 것은 다르다.
- **표는 숫자를 견줄 때만.** 설명을 표에 밀어 넣으면 문장으로 읽으면 3초일
  것을 표에서 찾게 만든다.
- **좌표는 사용자가 열어 볼 자리에만.** `file:line` 은 리뷰에서 필수지만
  대화에서는 대부분 잡음이다.
- **자기 판단을 변호하지 않는다.** "저는 이쪽이 낫다고 봅니다" 는 길이만
  늘린다. 무엇을 하겠다고 쓰면 된다.

**대화는 되물을 수 있다는 것이 차이다.** PR 본문은 잘못 쓰면 오해된 채로
지나가고, 대화는 *"그게 무슨 뜻이야"* 가 돌아온다. 그것이 느슨하게 써도 된다는
뜻은 아니다 — 되묻는 데 한 번의 왕복이 들고, 맞는 단어를 골랐으면 안 들었을
왕복이다.

```
나쁨   세 구간 전부 동일합니다. 재발견에 관한 것이라 준수율이 0 입니다.
좋음   명령이 실제로 돌아간 시간은 15분이고, 다음 명령을 내보내기까지
       30분이 갔습니다. 한 번에 하나씩만 보내고 있었습니다.
```

바뀐 것은 사실이 아니라 **이 저장소가 만든 말을 하나도 안 쓴 것**이다.
